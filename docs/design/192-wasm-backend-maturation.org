* 1. Problem, measured on this clone

** 1.1 What has actually shipped (correcting an over-broad read of "not usable")

Doc 165 (mobile deployment, sibling doc, already ACTIVE) states plainly
that "The wasm backend (Doc 164, all of P0–P4) is COMPLETE" — and this
is independently verifiable, not just cited: =site/dtw/dtw.js= exists
and its =env= import object contains exactly the shape the P4
blueprint specified (=key_state=, =frame_out=), =lisp/nelisp-asm-wasm.el=
has a real =nelisp-asm-wasm-op-memory-grow= emitter (P3's bump
allocator prerequisite), and the =Makefile= has a full
=wasm-dtw-skeleton-smoke -> wasm-dtw-transpile -> wasm-dtw-compile ->
wasm-dtw-smoke -> wasm-dtw-site -> wasm-dtw-site-smoke= pipeline. This
is a real, shipped, curated application running compiled Elisp in a
browser. =recipes/README.org= corroborates at the recipe-shape level:
"WASM / browser | compiles and runs | =make wasm-smoke= compiles two
Elisp functions to wasm32, validates both modules and executes them
under node, on Windows and Linux alike (2026-08-18)." So the framing
"wasm doesn't work" is wrong; the honest framing is narrower, and §1.2
locates it precisely.

** 1.2 The actual wall: the generic builtin-call bridge, not arithmetic, not P0-P4's own scope

=nelisp-aot-compiler--parse-extern-call-args= (the shared parser behind
every =extern-call=, including the =nelisp_aot_builtin_calln= bridge
every non-specially-lowered builtin call goes through) enforces a GP
argument-register budget:

#+begin_src elisp
(when (and (> (length gp-args)
              (length (nelisp-aot-compiler--current-arg-regs)))
           (not (and (eq nelisp-aot-compiler--arch 'x86_64)
                     (memq nelisp-aot-compiler--abi '(sysv win64)))))
  (signal 'nelisp-aot-compiler-error
          (list :extern-call-too-many-gp-args name (length gp-args))))
#+end_src

=--current-arg-regs= dispatches on architecture — =aarch64= gets its own
8-register list, =win64= gets its own list — but wasm has *no dedicated
case*. It falls through to the =(t nelisp-aot-compiler--arg-regs)=
default, which is the plain *x86_64 SysV* register list: =(rdi rsi rdx
rcx r8 r9)=, six entries. And because wasm is not =x86_64=, it is also
not in the exempted set that gets stack-argument spilling for an
over-budget call — so once six GP arguments are in flight, any further
argument is a hard compile error on wasm specifically, with no
fallback path at all (x86_64 SysV/Win64 have one; wasm does not).

=nelisp_aot_builtin_calln='s own fixed ABI prefix — =mirror, frames,
name, argc, out, scratch= — is *six* arguments, before a single user
argument is added (=(extern-call nelisp_aot_builtin_calln ,mirror
,frames ,name-slot ,argc ,out ,scratch ,@lowered-args)=,
=lisp/nelisp-aot-compiler.el=). Six fixed arguments against a six-slot
budget that has no spill path on wasm means *any* =calln=-routed
builtin call taking one or more user arguments fails to compile for
wasm today — not "beyond a large N," beyond *zero*. This is measured
directly against this clone's source, not inferred: the design brief's
figure of "8 gp args" does not match what =--current-arg-regs= actually
returns for wasm (six, via the x86_64-shaped fallback, not eight, which
is aarch64's own separate list) — worth stating plainly, because it
changes the fix (§3): the ceiling is not merely too low, it is set by
omission to a completely unrelated architecture's physical register
count, for a target that has no physical registers at all.

This is exactly why "arithmetic" is what currently survives: =+=/=-=/
=*=/=mod=/comparisons compile to direct wasm value-stack instructions
(=nelisp-aot-compiler--emit-arith=, its wasm arm; the =mod= emitter
studied in Doc 190 §1.2 for its overflow comment) and never touch
=calln= or =--parse-extern-call-args= at all. Named-function calls that
lower to direct =call $funcidx= (IR tag 5, same-module or resolved
import) and P2's environment-import mechanism (IR tag 23, the
=nelisp-aot-compiler--wasm-emit-call-import= arm, which *already*
constructs a wasm function type keyed purely by =(length args)= — see
§1.3) also survive, because neither goes through the six-slot GP-
register gate at all. Only the vararg/generic *builtin dispatch*
bridge — the path every builtin without a specially-lowered direct
call goes through — hits the wall.

** 1.3 Why this is a cheap fix, not a hard one: the wasm side already generalizes over arity

The P2-implemented environment-import arm
(=nelisp-aot-compiler--wasm-function-index= /
=--wasm-call-type-key= at the =(= tag 23)= case,
=lisp/nelisp-aot-compiler.el=) already builds its wasm function *type*
key from =(length args)= with no upper bound and no register concept at
all — a wasm function type is just a list of value-kind slots
(=i64=/=f64=), and the module's type section can declare as many
distinct arities as the compiler emits calls for. There is no ISA-level
"six GP registers" constraint on wasm the way there genuinely is on
x86_64 SysV or AAPCS64 — the six-slot ceiling measured in §1.2 is
*purely* an artifact of =--current-arg-regs= reusing a native-ISA-
shaped list for a target that does not have that ISA's constraint,
not a real limit this backend has to engineer around. This is the
single most load-bearing fact in this doc: lifting the ceiling for
wasm is not "design a stack-spill ABI" (the hard problem x86_64/aarch64
genuinely have); it is "stop pretending wasm has six physical
registers."

* 2. Decided direction

**Give wasm its own =--current-arg-regs= entry, sized generously (not
matched to any native ISA's register count, because none applies), and
confirm the calln runtime bridge's =env= import signature — the host-
side function Node/the browser actually implements — accepts that
arity. Do not attempt a stack-spill ABI for wasm; §1.3 already showed
none is needed.**

This is deliberately the smallest fix that removes the actual wall.
Two things have to be verified, not assumed, before calling it done:

1. *The compiler side*: extending =--current-arg-regs= with a =wasm32=
   branch returning a placeholder list long enough for real corpus
   forms (the multi-arg builtins the parity corpus already exercises
   are the right sizing signal — see §4) removes the compile-time
   error. This does not by itself prove the *runtime* bridge works;
   §2.2 is separate.
2. *The runtime bridge side*: =nelisp_aot_builtin_calln='s current wasm
   lowering, once it compiles at all under a raised ceiling, needs its
   host-side counterpart (whatever plays the role =site/dtw/dtw.js='s
   =env= object plays for the DTW recipe) to actually exist and
   correctly dispatch by symbol name with the received argument count.
   This is new work, not already covered by P0-P4's shipped scope —
   DTW's =env= object is curated for DTW's own thirteen-ish import
   needs (§1.1), not a general builtin dispatcher. Building *that* is
   the second, larger half of this doc's next tranche, and is scoped
   separately from the ceiling fix in §3's phasing because the ceiling
   fix is verifiable in isolation (does it compile) while the runtime
   bridge needs an actual host harness to test against (Node, per Doc
   164 §0's own verification stance: "Node.js v24.14.1 is installed...
   it is the harness").

* 3. Phased plan

** Phase A — lift the compile-time ceiling only

Add the =wasm32= case to =--current-arg-regs=. Pick the list length
from the parity corpus's own actual maximum builtin-call arity (measure
first, do not guess a round number) plus headroom. Verify: every
corpus form that previously failed to compile for wasm specifically
because of =:extern-call-too-many-gp-args= now compiles (a clean,
mechanical, git-log-style before/after diff of compiler errors across
the fixed corpus — the same "measured before, measured after" discipline
this repo's own recent commits, e.g. =342d098cc='s explicit
before/after probe output, already model). This phase does *not* touch
the runtime bridge and does not by itself make any new form *run*
correctly — only *compile*.

** Phase B — the calln runtime bridge's wasm-side host import

Design (separately, and this doc does not attempt the design here,
because it depends on decisions Phase A's measurement should inform —
specifically, how many distinct symbol names actually need dispatch
through =calln= once direct-call and env-import lowering have taken the
cases they already handle) a general symbol-dispatching host import,
analogous to =nelisp_aot_builtin_calln='s native-side bridge
(=nelisp-cc-runtime-aot-builtin-calln=, =src/nelisp-cc-runtime.el=,
which resolves a symbol name to a builtin and dispatches via
=nelisp--apply=/=apply=) but implemented as a wasm =env= import backed
by the same host process the module is instantiated in — Node today,
a browser under P4's precedent tomorrow. This is real, unscoped-yet
implementation work; Phase B's deliverable in *this doc* is only
"confirm this is the right shape by getting one previously-uncompilable
multi-arg builtin call to round-trip end-to-end under Node," not a
production dispatcher.

** Phase C — broaden past the DTW-curated import surface

Doc 164 §1.3's own accounting — ~453 =extern-call= sites, ~13 libc + 3
libm + a 55-site =syscall-direct= table as the genuine host-import
surface, the overwhelming rest resolving intra-module — is the honest
starting inventory for "what would a *general* NeLisp-on-wasm program
need from its host," as distinct from what DTW specifically needed
(=key_state=/=frame_out=, a two-function surface sized to one game
recipe). Phase C is not designing that whole surface (out of scope for
this doc, and premature before Phase A/B's measurements exist) — it is
naming that the DTW =env= object is not evidence the general surface is
solved, only that a curated subset of it is, and that the corpus-driven
approach in §4 is how the *next* real subset gets chosen, rather than
guessing at "everything libc-shaped" up front.

* 4. Defining "mature enough": a corpus-rows-passing ladder

The design brief asks for "mature enough" to be defined by
corpus-rows-passing rather than left qualitative, and the substrate-
parity corpus already gives this doc a ready-made, already-measured
instrument to reuse rather than invent: =tools/nelisp-substrate-
parity.el='s =--substrate-order= constant currently lists exactly six
substrates — =load, runtime-image, artifact, source-cache,
source-fallback, host= — run against a fixed corpus
(=tools/nelisp-substrate-parity-corpus.el=, 215+ forms as of this
week's =defvaralias= commit) plus a =bare= baseline. *There is no
=wasm= entry.* That absence is this doc's literal starting rung, not a
citation — checked directly against =--substrate-order='s definition on
this clone.

| rung | wasm substrate-parity status                                        | gate                                  |
|------+-----------------------------------------------------------------------+----------------------------------------|
|    0 | (current) no =wasm= entry in =--substrate-order= at all              | none — this is where the tree stands  |
|    1 | =wasm= entry added, scoped to the corpus subset that compiles *today* (arithmetic, comparisons, direct/env-import calls — no =calln=-routed multi-arg builtins) | =checked= count reported, =findings= tracked the same way every existing substrate already is; no threshold yet |
|    2 | Phase A (§3) lands; re-run the *same* corpus subset used at rung 1 plus every form that was previously =:extern-call-too-many-gp-args=-blocked and now compiles | measure the *delta* in corpus rows that compile — this is the number Phase A should be judged by, not a subjective "feels better" |
|    3 | Phase B (§3) lands; re-run and measure rows that *run correctly*, not just compile — matched against the same "KNOWN GAP" acceptance discipline =tools/substrate-parity-accepted.el= already applies to =source-fallback= (currently ~20 accepted gaps for primitives =nelisp--primitive-symbols= omits, per that file's own comments) — wasm is allowed the same class of accepted, *named*, individually-justified gap, not held to a stricter zero-tolerance bar than an existing substrate already gets |
|    4 | "mature enough to gate": wasm's =checked=/=findings= ratio reaches parity with =source-fallback='s current standing (the substrate this repo's own convention already treats as the acceptable floor, not =load='s or =host='s stricter bar) — *this* is the number that should decide whether =wasm-smoke=-class checks move from optional (§5) to required in =tools/ai/gates.expected=, not a round percentage picked without reference to how this repo already treats its other substrates |

Rung 4 deliberately anchors "mature enough" to an *existing* internal
bar (source-fallback's accepted-gap count) rather than to "0 findings,"
because 0 findings is not the bar this repo holds any of its other
five substrates to today, and holding wasm to a stricter standard than
=source-fallback= — which has real, long-standing, individually-
justified gaps against Emacs baked into
=tools/substrate-parity-accepted.el= right now — would be inventing a
new, harsher policy specifically for wasm with no stated reason to.

* 5. Verification design

- *Phase A*: a fixed before/after compiler-error diff over the corpus,
  the same "unfixed binary, then fixed binary, same probe" discipline
  this week's =342d098cc= commit used for the intern fix — not a claim
  of "it should work now," a captured list of which specific corpus
  forms flip from erroring to compiling.
- *Phase B*: an end-to-end Node run (Doc 164 §0's stated harness) of
  one previously-blocked multi-arg builtin call, output captured via
  the same artifact-not-scrollback discipline AI.md rule 4 requires —
  =node ... > target/ai/wasm-calln-probe.txt= or equivalent, read from
  the file.
- *Rungs 1-4 (§4)*: wired as a new, *optional* gate initially (matching
  how =wasm-smoke= is already listed optional in
  =tools/ai/gates.expected= — "Optional only because it needs node; it
  passes on both hosts measured so far") — a =wasm-substrate-parity?=
  entry reporting =checked=/=findings= the same shape every other
  substrate-parity run already reports, promoted to required only once
  rung 4's threshold is measured, not assumed, to hold — the same
  promotion discipline this repo already applies elsewhere (per AI.md's
  own rule: "A gate that executed zero cases is not green").
- *Regression protection once wasm joins substrate-parity*: the corpus
  is shared infrastructure — any future corpus addition (for any
  substrate) automatically becomes a wasm-substrate obligation too,
  which is a real, ongoing cost this doc states plainly rather than
  hides: adding a =wasm= entry to =--substrate-order= is not a one-time
  fix, it is opting the wasm backend into every future corpus growth
  the other six substrates already absorb.

* 6. Open questions

- What is the corpus's actual maximum builtin-call arity today (§3
  Phase A asks this be measured, not guessed)? This doc does not have
  that number — it requires running the corpus generator/parser against
  the current 215+-form corpus and is a five-minute measurement this
  doc's author did not have a built binary in hand to perform (design-
  only session, per this doc's own scope).
- Does the =env= import object's function-type arity need to match
  *exactly* per call site (as DTW's two-function, fixed-signature
  =env= object does), or can Phase B's general dispatcher use a single,
  fixed-arity "argv in linear memory" import (mirroring how x86_64
  SysV's own stack-spill path already handles over-budget native calls,
  §1.2) instead of one wasm function type per distinct arity? The
  latter would sidestep needing to grow the type section per new arity
  encountered, at the cost of an extra linear-memory marshal step on
  every =calln= call — a real design decision Phase B should make with
  a measurement, not assume either way here.
- Whether the =syscall-direct= 55-call-site table (Doc 164 §1.3) has
  any overlap with what a general =calln= dispatcher (Phase B) would
  also need to route through =env= imports, or whether the two paths
  are cleanly disjoint (calln for Elisp-level builtins, syscall-direct
  for OS-level primitives) — not verified in this doc; worth checking
  before Phase C scopes the general import surface, since double-
  counting or double-implementing either path would be wasted work.
- Rung 4's anchor (source-fallback parity) assumes source-fallback's
  own accepted-gap count stays roughly stable going forward. If Doc
  168's own follow-up work (closing the =nelisp--primitive-symbols=
  gap that produces most of source-fallback's current accepted list,
  per §4's citation) lands first, the anchor point moves — this doc's
  rung 4 should be re-measured against whatever source-fallback's
  standing is at the time wasm actually approaches it, not against the
  number quoted here today.
