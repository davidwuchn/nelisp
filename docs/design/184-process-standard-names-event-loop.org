#+AUTHOR: nelisp / nelisp-emacs (design: Claude Opus 5 + zawatton)
#+DATE: 2026-08-22
#+STATUS: DRAFT — design only, no feature code in this doc.

* §0 TL;DR

The standalone reader already has real, working async subprocess machinery:
a native spawn/pipe/poll/wait/exit family under the =nelisp-process-*= prefix
(=nelisp-process-start=, =-poll=, =-read-output=, =-write=, =-close-stdin=,
=-wait=, =-object-p=, =-pid=, =-status=, =-exit-status=, =-delete=,
=-call-process=), proven this session by =make standalone-reader-process-smoke=
(=Makefile:1652-1668=) against real =/bin/sh=, =/bin/cat= children — PASS.  It
also has a real cooperative event loop with a deadline-ordered timer queue and
genuine =poll(2)=-based blocking
(=packages/nelisp-eventloop/src/nelisp-async.el=), and a *second*,
differently-shaped multi-fd registration API
(=packages/nelisp-eventloop-multiplex/src/nelisp-eventloop-multiplex.el=)
whose only working backend depends on being hosted inside real Emacs.  What is
missing is not the substrate — it is the *adapter*: nothing currently wires
=nelisp-process-*= spawn to standard Emacs names (=make-process=,
=set-process-filter=, =set-process-sentinel=, =accept-process-output=,
=make-network-process=) in a way that survives contact with the standalone
binary, and nothing pumps process readiness through the one loop that already
knows how to block efficiently.

Three measured, specific defects anchor the design:

1. =run-at-time='s *default* prelude stub fires its FUNCTION synchronously,
   once, ignoring REPEAT (=scripts/nelisp-stdlib-prelude.el:2377-2389=,
   =tools/partial-accepted.txt= line =run-at-time|...|_repeat|REPEAT
   ignored:...=) — confirmed this session: scheduling a repeating timer via
   =(run-at-time 0 1 FN)= runs FN exactly once, synchronously, before the call
   even returns.
2. The prelude's *own* =make-process= (=scripts/nelisp-stdlib-prelude.el:6030-6051=)
   *does* correctly call =nelisp-process-start= when it is =fboundp= and *does*
   track =:sentinel= via =process-put= for later draining — but drops =:filter=
   entirely (no plist-get for it anywhere in the function), and
   =accept-process-output= (=:6075-6091=) ignores its own PROCESS/SECONDS
   arguments (=&rest _args=) and always blocks until *every* pending process
   fully exits via =nelisp-process-wait=, not Emacs's bounded single poll.
3. A *second*, independently-written adapter,
   =packages/nelisp-process/src/nelisp-process.el= (1154 lines, Doc 39-era,
   =nelisp-make-process= et al. under an =nelisp-= prefix, not bare names),
   degrades on the standalone binary specifically: its constructor's
   =(if (fboundp 'nelisp-process-start) (apply #'nelisp-process-start command)
   ...)= (=:413-414=) takes the *native* branch precisely when running inside
   =target/nelisp=, and that branch discards every keyword — =:filter=,
   =:sentinel=, =:buffer=, =:actor=, =:coding= — and returns the bare native
   process handle instead of the =nelisp-process= =cl-defstruct= every other
   function in the file expects.  The file's own "Emacs-compatible" filter/
   sentinel/actor wiring only exists in the *host-Emacs fallback* branch
   (=:415-459=), which is dead code on the binary this doc is about.

*Recommendation*: keep both existing loop implementations, but stop treating
them as competitors. =nelisp-async.el= is the real, standalone-native,
already-=poll(2)=-driven loop; extend its fd set from "stdin + timers" to "N
registered fds + timers" (a small, well-scoped change — its poll primitive
already takes an arbitrary =fd=, see §3.2) and make it the loop of record for
the standalone binary. Repoint =nelisp-eventloop-multiplex='s public
API (=register-fd=/=tick=/=run=/=stop=, which is the nicer, more general
shape) at that native backend instead of its current Emacs-only
=host-bridge=. Fix the prelude's =make-process=/=accept-process-output= to
carry =:filter=, respect PROCESS/SECONDS, and register spawned processes with
the loop instead of doing a private eager drain. Add bare-name aliases
(=set-process-filter=, =set-process-sentinel=, =process-send-string=) using
this codebase's own =(unless (fboundp 'NAME) (defun NAME ...))= idiom.  Retire
=packages/nelisp-process/src/nelisp-process.el='s native branch to a thin
call into the fixed prelude functions rather than bypassing them.

* §1 Problem — measured evidence

** §1.1 What is real today: native process primitives

=scripts/nelisp-standalone-build.el:9347-9392= registers twelve
=nelisp-process-*= names as native dispatch entries (=nl_bi_process_*=, an
assembler-emitted "applyfn" unit — the same mechanism that backs every other
native subr in the shipped binary, see Doc 187 §1.2 for the sibling family
covering =+=/=-=/=*=).  Verified working, this session, via
=make standalone-reader-process-smoke= (=Makefile:1647-1668=):

#+begin_example
[standalone-reader-process-smoke] PASS: call-process exit=7,
  read-output -> "process-smoke-ok",
  cat -> (13 "cat-roundtrip" 1 1 0),
  poll -> (0 0 1 1 "sleepy")
#+end_example

This exercises real =fork=/=exec=/pipe read/write/poll/wait against
=/bin/sh=, =/bin/cat= — not a mock, not a host-Emacs bridge.  This is the
correct foundation layer; nothing in this doc proposes replacing it.

Separately, =make-network-process= is *already* a bare-named native subr:
=src/nelisp-eval.el:757-767= lists =make-process=, =process-send-string=,
=process-send-eof=, =process-live-p=, =process-status=, =process-exit-status=,
=kill-process=, =delete-process=, =accept-process-output=, =process-id=,
=process-name=, =process-command=, =process-buffer=, =set-process-sentinel=,
=set-process-filter=, and =make-network-process= as
=nelisp--primitive-symbols= — but see §1.3: this list only installs a name
when it is *already* =fboundp= at bootstrap, and measured =fboundp= results on
=target/nelisp= (this session) are:

#+begin_example
(fboundp 'make-process)          => t
(fboundp 'make-network-process)  => nil
(fboundp 'nelisp-process-start)  => t
(fboundp 'set-process-filter)    => nil
(fboundp 'accept-process-output) => t
#+end_example

=test/nelisp-stdlib-test.el:767-771= independently asserts
=(subrp (indirect-function 'make-network-process))= as a *host-Emacs* ERT
expectation (=nelisp-eval=, run under =make test=) — it says nothing about the
standalone binary, where the probe above shows =make-network-process= void.
=make-process= and =accept-process-output= being =t= is explained in §1.2:
they are prelude-level =defun=s, not a second native family.

** §1.2 The prelude's own adapter (real, partial)

=scripts/nelisp-stdlib-prelude.el= defines bare =make-process= (:6030-6051),
=call-process= (:6055-6067), =start-process= (:6069-6071), and
=accept-process-output= (:6075-6091), each guarded
=(unless (fboundp 'NAME) ...)=.  Read in full, =make-process= is a real
adapter, not a stub: it resolves the command via =executable-find=, calls
=nelisp-process-start= when native, tags the returned process with =:name=/
=:sentinel=/=:stderr= via =process-put=, and pushes it onto
=nelisp--pending-processes= (=:5812=) for later draining.  Two measured gaps:

- *No =:filter=.*  The =plist-get= list at =:6033-6036= is
  =name command stderr-buffer sentinel= — =:filter= is never read, so a caller
  that passes =:filter= gets silent, total data loss of that keyword; nothing
  ever streams incremental output to it.
- =accept-process-output='s signature is =(&rest _args)= (=:6075=) — the
  PROCESS argument Emacs uses to wait on *one* process is discarded, and so is
  SECONDS.  The real behaviour (=:6076-6091=) drains *all* of
  =nelisp--pending-processes= and calls =nelisp-process-wait= (block until
  *exit*) on each — not a single bounded poll.  A caller doing
  =(while (accept-process-output proc 0.1) ...)= to stream a long-lived
  process's output incrementally gets one call that blocks until every
  pending process, including unrelated ones, has *exited*.

=:sentinel= *is* wired end to end: =(process-get proc :sentinel)= is read back
inside =accept-process-output= (=:6086-6088=) and funcalled with
=(proc "finished\n")= once the process is drained — the sentinel path works,
just only reachable through the drain-everything call shape above.

** §1.3 =nelisp-eval.el='s primitive install is fboundp-gated, not a guarantee

=src/nelisp-eval.el:923-944= (=nelisp--install-primitives=) only copies a
symbol from =nelisp--primitive-symbols= into the interpreter's function table
=when (fboundp sym)= at the moment installation runs — its own docstring says
so plainly: "=nelisp--primitive-symbols= assumes a real-Emacs host, where
every entry ... is always =fboundp=.  On the standalone NeLisp runtime's own
bootstrap substrates that assumption does not hold for every entry."  This
means the presence of a name on that list is not evidence it works on
=target/nelisp= — =make-network-process= is on the list and void there;
=make-process= is on the list and *is* fboundp there only because the prelude
above independently defines it first.  Doc 184's design must not lean on this
list as a source of truth; it is a compatibility hedge for a *different*
execution mode (see §1.6).

** §1.4 A second adapter that silently degrades on this exact binary

=packages/nelisp-process/src/nelisp-process.el= (1154 lines, header cites
"Phase 9d.L per Doc 39") implements a fuller keyword surface —
=cl-defun nelisp-make-process (&rest args &key name command connection-type
coding buffer sentinel filter actor props stderr noquery stop file-handler
keepalive tty pty-name remote http-buffer match &allow-other-keys)=
(=:365-368=) — under =nelisp-=-prefixed names, with real sentinel/filter
trampolines, actor event posting, and eventloop-multiplex registration *in
its host-Emacs fallback branch only*.  Its body opens:

#+begin_src elisp
(if (fboundp 'nelisp-process-start)
    (apply #'nelisp-process-start command)
  (let* (... full :filter/:sentinel/:buffer/:actor wiring via host make-process ...))
#+end_src

(=:413-459=).  On =target/nelisp=, =nelisp-process-start= is native and
=fboundp=, so *every* call to =nelisp-make-process= takes the first branch:
=command= here is only the =:command= keyword's value (the argv list, via the
=cl-defun= =&key= destructure) — every other keyword, including =:filter= and
=:sentinel=, is silently dropped, and the return value is the *bare* native
process handle, not the =nelisp-process= =cl-defstruct= that
=nelisp-process-send-string=, =nelisp-process-host-proc=, and the rest of the
file's ~40 other functions assume they were handed.  This is a textbook
instance of this project's own rule 1 in AI.md ("a gate that executed zero
cases is not green") turned into "an adapter that was proven only against the
branch it does not ship on" — its own test file's header
(=packages/nelisp-process/test/nelisp-process-test.el:1-20=) describes
coverage of exactly the filter/sentinel/buffer semantics that the native
branch bypasses, with no indication those tests are ever run against
=target/nelisp= rather than host Emacs.

** §1.5 The event loop: two implementations, one real, one Emacs-only

=packages/nelisp-eventloop/src/nelisp-async.el= (303 lines) is genuinely
standalone-native: =nelisp-async-run-at-time= (=:78-90=) maintains a
deadline-ordered timer queue (vector =[DEADLINE REPEAT FN ARGS LIVE]=,
=:63-68=) that *does* honour REPEAT, =nelisp-async--nanosleep= sleeps via the
=nl-nanosleep= builtin (real =clock_nanosleep=, not a spin loop), and
=nelisp-async-run-tty= (=:245-260=+) multiplexes timer deadlines with a *single*
TTY fd (default stdin) via raw =syscall-direct=-based =poll(2)=
(=nelisp-async--poll-fd=, =:181-190=).  This file upgrades =run-at-time=/
=cancel-timer=/=sit-for= from the prelude's synchronous stubs the moment it is
loaded (its own header says so, =:1-15=) — but nothing loads it by default in
the standalone-reader build, and it has *zero* knowledge of processes: it was
built to solve "timers + one keyboard fd", not "timers + N process pipes".

=packages/nelisp-eventloop-multiplex/src/nelisp-eventloop-multiplex.el= (539
lines, "Doc 39 §3.K") has the *right-shaped* public API for this doc's goal —
=nelisp-eventloop-multiplex-register-fd FD TYPE CALLBACK=,
=-tick=, =-run=, =-stop= (=:16-40=) — but its own commentary is explicit that
the only shipped backend, =='host-bridge'=, "maps NeLisp fd integers onto host
Emacs process objects" and probes readiness via *host* =process-status= +
=accept-process-output PROC 0= (=:59-65=); the real =nl_syscall_select=-backed
=='rust-ffi'= backend is "reserved for Phase 7.5" and does not exist.  On
=target/nelisp= there is no host Emacs process object to bridge to, so this
module's only working backend is unreachable from the binary this doc is
about.  =nelisp-process.el='s own eventloop registration
(=nelisp-process--register-eventloop=, referenced =:353-360=) calls into this
same host-only backend, wrapped in =ignore-errors= — meaning on the
standalone binary that registration call *silently no-ops* every time, which
is exactly the "stub's return value silently breaks a downstream caller"
pattern this project's memory already tracks
(=feedback-stub-silent-downstream-breakage=).

** §1.6 The loop that exists is not reachable from an interactive app today

=recipes/README.org:26= records the *measured* verdict for the shape this
doc directly enables: "TUI (async event loop) | fails today |
=tools/nelisp-async-tty-smoke.sh= dies with =void-variable: (declarations)=
loading the host =generator.el=".  Reading the smoke
(=tools/nelisp-async-tty-smoke.sh:15-26=): it loads =nelisp-actor.el= before
=nelisp-eventloop.el=/=nelisp-async.el=, and =nelisp-actor.el= apparently
depends on host Emacs's =generator.el= (CPS macros, =iter-defun=) for its
scheduler, which the standalone reader cannot load correctly.  This is
*outside* this doc's scope to fix (it is an actor/generator compatibility gap,
not a process/timer one) but it means today's real loop
(=nelisp-async-run-tty=) is blocked from ever running end to end by a
dependency this doc does not touch — recorded here so the phased plan in §4
does not silently assume it away (see §6.3).

=docs/design/33-nelisp-v1x-architecture.org= (status =LOCKED-2026-04-25-v2=)

whether Doc 33 should be amended to say so.

* §2 Decided direction

1. *One loop, native-first.* =nelisp-async.el= becomes the loop of record for
   the standalone binary. Generalize its single hardcoded stdin =poll(2)= call
   into an N-fd registration table (§3.2) — a moderate, well-scoped change,
   since =nelisp-async--poll-fd= (=:181-190=) already takes an arbitrary =fd=
   argument; the work is building the *set* on top of the existing primitive,
   not inventing new syscall plumbing.
2. =nelisp-eventloop-multiplex='s public shape (=register-fd=/=tick=/=run=/
   =stop=) is kept as the *stable public API* other packages already code
   against (=nelisp-process.el='s registration call, =nelisp-eventloop-as-
   event-source-pull-fn='s Doc 34 §2.4 contract) — but its =='host-bridge'=
   backend is renamed/documented as exactly what it is (an Emacs-hosted
   compatibility shim, not the standalone path), and a new backend,
   provisionally =='native'=, is added that implements =-tick='s select
   semantics by delegating to the same raw =syscall-direct=-based =poll(2)=
   §3.2 adds to =nelisp-async.el=. This explicitly does *not* touch Rust —
   per this project's own hard rule (=feedback-nelisp-rust-loc-never-
   increase=), the earlier =='rust-ffi'= placeholder name should be
   understood as superseded, not implemented.
3. Fix the prelude's =make-process= to read and store =:filter=
   (=process-put proc :filter filter=, mirroring the existing =:sentinel=
   line) and register the new process with the loop's fd set instead of only
   =nelisp--pending-processes=; fix =accept-process-output= to honour its
   PROCESS argument (single-process poll, not drain-all) and SECONDS (a
   bounded, non-blocking =nelisp-process-poll= loop via the timer/nanosleep
   primitives already in =nelisp-async.el=, not an unconditional
   =nelisp-process-wait=).  Filter dispatch: when new output is available (via
   =nelisp-process-poll='s ready bit) and =:filter= is set, funcall it with
   =(proc chunk)= from =nelisp-process-read-output=; otherwise preserve the
   existing default "append to process-buffer" behaviour.
4. Add bare-name aliases for the standard surface the standalone binary is
   missing (=set-process-filter=, =set-process-sentinel=,
   =process-send-string=, =process-send-eof=) using the codebase's own
   established idiom, =(unless (fboundp 'NAME) (defun NAME (...) ...))=, so a
   host-Emacs load that already has the real subr is untouched.
   =make-network-process= is deliberately *out of scope* for this doc (§6.4):
   it is void on =target/nelisp= today and has no native primitive family
   analogous to =nelisp-process-*= to adapt — designing it needs its own pass
   over =packages/nelisp-network/src/nelisp-network.el= and the =nl_bi_*=
   dispatch surface, which this doc's evidence base does not yet cover.
5. =packages/nelisp-process/src/nelisp-process.el='s native branch
   (=:413-414=) is replaced with a call into the fixed prelude =make-process=
   (passing through all keywords) rather than a bare
   =(apply #'nelisp-process-start command)= — so the =nelisp-=-prefixed
   surface becomes a thin, keyword-complete wrapper around the one real
   adapter instead of a second, divergent implementation.
6. *Loop pump*: both REPL idle and an explicit =accept-process-output= are
   wired to the same =nelisp-async--fire-due=/poll step (mirroring real
   Emacs, which also services process/timer events at both points) — see
   §3.3 for exactly where each hooks in.

* §3 Design detail

** §3.1 Process object shape

Keep the prelude's =(vector 'process NAME nelisp-process-start-handle
PROPS-ALIST)=-style representation (matching =processp='s existing check at
=scripts/nelisp-stdlib-prelude.el:5892-5895=, which already accepts *either* a
tagged vector *or* a raw =nelisp-process-object-p= handle) rather than
introducing a third struct shape — =process-get=/=process-put=
(=:5908-5924=) already round-trip an alist in vector slot 4 for the tagged
case and a side-table (=nelisp--process-props=) keyed by the raw handle for
the native case.  Doc 188 (buffer unification) independently recommends a
single canonical buffer representation for the same reason: two representations
of "the same kind of object" is exactly the class of bug §1 measured.

** §3.2 Generalizing =nelisp-async='s poll from 1 fd to N

Current: =nelisp-async--poll-fd FD TIMEOUT-MS= (=packages/nelisp-eventloop/
src/nelisp-async.el:181-190=) builds one =pollfd= struct via =alloc-bytes 8 8=
and calls =syscall-direct 7 pfd 1 timeout-ms 0 0 0= (=poll(2)= with =nfds=1=).
Generalizing to N fds means allocating =8*N= bytes, writing one =pollfd= entry
per registered fd (fd | (POLLIN << 32), matching the existing single-fd
encoding at =:184=), calling =poll(2)= with =nfds=N=, and walking the result
array to find which entries have =revents & (POLLIN|POLLHUP)= set — the same
per-entry decode already used at =:187-190=, just looped.  This is additive:
=nelisp-async-run-tty='s existing single-fd call becomes the =N=1= case of the
general one, so no existing caller's behaviour changes.

** §3.3 Where the loop is pumped

Emacs itself services process output at both explicit =accept-process-output=
calls *and* at idle points inside the command loop (redisplay/sit-for). This
doc mirrors that dual entry, since transient/magit-class code (Doc 185's
consumer) calls =accept-process-output= directly in some paths and relies on
background delivery via idle/timer in others:

- *Explicit*: the fixed =accept-process-output= (§2.3) calls the generalized
  N-fd poll (§3.2) with the caller's SECONDS as the timeout, dispatching any
  ready fd's =:filter= and any exited process's =:sentinel= before returning.
- *REPL idle*: the standalone reader's REPL (=--repl= flag, per =nelisp --help=)
  gets one call to the same poll-and-dispatch step, zero-timeout, between
  reading forms — piggybacking on =nelisp-async-sit-for='s existing due-timer
  loop (=:134-146=) rather than adding a second polling site.
- Both paths call the *same* underlying dispatch function, so there is exactly
  one place that decides "fd ready -> call filter" / "process exited -> call
  sentinel", which is the one-event-loop requirement this doc is titled for.

* §4 Phased plan with costs

Costs are engineer-days against this design, assuming the researcher who
wrote this doc implements it (familiar with the codebase already).

** P0 — Fix the prelude adapter in place (1 d)
- Add =:filter= to =make-process='s =plist-get= list and =process-put= it.
- Rewrite =accept-process-output= to honour PROCESS (single-fd/-handle poll)
  and SECONDS (bounded via =nelisp-async--nanosleep=-style sleep, falling back
  to a busy =nelisp-process-poll= loop with a short sleep if =nelisp-async.el=
  is not loaded — see §6.2), dispatching =:filter= on new output.
- *Exit*: a new =Makefile= smoke, =standalone-reader-process-filter-smoke=,
  spawns =/bin/sh -c 'sleep 0.2; printf chunk'=, calls =accept-process-output=
  with a 1s timeout, and asserts the registered filter received =\"chunk\"=
  and the sentinel received the exit event — both currently unreachable
  because =:filter= is dropped today.

** P1 — Generalize =nelisp-async='s poll to N fds; register process fds (2 d)
- §3.2's N-fd =poll(2)=; a registration table (fd -> (TYPE CALLBACK CONTEXT))
  mirroring =nelisp-eventloop-multiplex='s existing shape so the API does not
  fork further.
- Wire =nelisp-process-start='s returned handle's underlying fd (needs a new
  =nelisp-process-fd= accessor over the native handle — a small addition to
  the =nelisp-process-*= dispatch table, §6.5) into this table on spawn.
- *Exit*: two concurrently-spawned processes (one fast, one slow) both have
  their filters invoked in real time via one =poll(2)= call each tick,
  verified by a smoke that asserts interleaved output order matches wall-clock
  completion order (not spawn order) — this is the concrete behavioural
  difference between "one real loop" and "sequential =nelisp-process-wait=".

** P2 — Point =nelisp-eventloop-multiplex= at the native backend (2 d)
- New =='native'= backend implementing =-tick='s contract via the P1 fd table
  instead of host =process-status=/=accept-process-output=.
- Update =nelisp-process.el='s =nelisp-process--register-eventloop= call to
  select this backend when =(fboundp 'nelisp-process-start)= (i.e. on the
  standalone binary) instead of unconditionally targeting =='host-bridge'=.
- *Exit*: =nelisp-eventloop-multiplex-register-fd= on a spawned process's fd,
  followed by =nelisp-eventloop-multiplex-run=, delivers a callback on real
  output without going through host Emacs at all — run this smoke with
  =NELISP_REPO= pointed at =target/nelisp=, not =emacs -Q=.

** P3 — Bare-name aliases + =nelisp-process.el= native-branch fix (1 d)
- =(unless (fboundp 'set-process-filter) (defun set-process-filter (proc f)
  (process-put proc :filter f)))= and the =set-process-sentinel=/
  =process-send-string=/=process-send-eof= equivalents.
- Replace =nelisp-process.el='s =:413-414= native branch with a call into the
  fixed =make-process= (passing all keywords through), so
  =nelisp-make-process= stops discarding =:filter=/=:sentinel=/=:buffer= on
  the standalone binary.
- *Exit*: =packages/nelisp-process/test/nelisp-process-test.el='s existing
  filter/sentinel/buffer-capture assertions pass when the suite is run
  *against =target/nelisp=* (a new run mode; today it is unclear this ever
  happens — see §1.4) as well as against host Emacs.

** P4 — REPL idle pump + timer-queue integration (1-2 d)
- Wire the =--repl= entry point's read loop to call the shared dispatch step
  (§3.3) at zero timeout between forms.
- Load =nelisp-async.el= by default in interactive/REPL contexts so
  =run-at-time= REPEAT actually repeats (§1's defect 1) without every caller
  needing to know to =(require 'nelisp-async)= first — gated so batch/CLI
  invocations (where the synchronous stub is arguably the *right* choice per
  the prelude's own comment, =scripts/nelisp-stdlib-prelude.el:2372-2376=)
  keep today's behaviour.
- *Exit*: an interactive smoke where a repeating =run-at-time= timer's
  callback fires more than once across successive REPL reads, and a
  concurrently-running child process's filter fires between REPL prompts
  without an explicit =accept-process-output= call.

Real Emacs semantics to hold every fixed function to, run via the
=nelisp-parity-probe= skill (=probe.sh -e FORM=) where a stock-Emacs answer

- =(let (r) (accept-process-output (start-process "x" nil "true") 0) r)= —

* §6 Open questions

** §6.1 Should Doc 33 be amended?

Doc 33 (LOCKED) assigns process control entirely to a not-yet-created
=nelisp-elisp-compat= package (§1.7).  This doc's P0-P3 work happens in
=scripts/nelisp-stdlib-prelude.el= and =packages/nelisp-eventloop*=/
=packages/nelisp-process=, none of which is that package.  Either Doc 33's
boundary line needs an explicit carve-out ("baseline process control ships in
core; the *editor-integration* surface — buffers-as-process-targets, TUI
redisplay hookup — is what stays deferred"), or this doc's work should be
reframed as *starting* =nelisp-elisp-compat= rather than extending the
prelude.  Not resolved here; flagged for whoever owns Doc 33's next revision.

** §6.2 Batch-mode =accept-process-output= without =nelisp-async.el= loaded

P0's bounded-SECONDS fix (§4) needs *some* sleep primitive when the caller has
not loaded =nelisp-async.el=.  A busy-poll loop calling =nelisp-process-poll=
in a tight cycle burns CPU; borrowing =nelisp-async--nanosleep= means either
loading part of that package unconditionally (scope creep on "one event
loop") or duplicating a nanosleep helper.  Which is cheaper needs a decision
before P0 lands, not deferred to implementation.

** §6.3 The =generator.el= dependency blocking the TTY path

§1.6's =tools/nelisp-async-tty-smoke.sh= failure (host =generator.el= will not
load standalone) blocks P4's *interactive* exit criterion specifically. If
that dependency is not fixed by whoever owns the actor/generator compat gap
before P4 is attempted, P4 may need to drop the TTY-multiplexed smoke and
settle for a REPL-only (no live keyboard) exit criterion — worth deciding
explicitly rather than discovering mid-implementation.

** §6.4 =make-network-process=

Deliberately out of scope (§2.4) for lack of evidence base — this doc's
research did not reach =packages/nelisp-network/src/nelisp-network.el= or the
native dispatch surface (if any) backing =make-network-process='s void state
on =target/nelisp=.  A sibling doc or a P5 extension of this one should cover
it once that surface is measured the way §1.1-§1.4 measured the process
family here.

** §6.5 =nelisp-process-fd= accessor

P1 (§4) assumes a way to get the underlying pollable fd out of a native
=nelisp-process-*= handle. No such accessor exists today (confirmed: the
twelve names in =scripts/nelisp-standalone-build.el:9347-9392= do not include
one). Whether this needs a new native dispatch entry or can be derived from
existing accessors (e.g. via =nelisp-process-object-p= internals) is
implementation work for P1, not resolved by this design.
