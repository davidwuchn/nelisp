#+AUTHOR: nelisp / nelisp-emacs (design: Claude Opus 5 + zawatton)

* §0 TL;DR

The elisp-layer completion on =origin/feat/stdlib-hooks-map-fixnum= (commit
=84950ad30=, not yet merged) bound =most-positive-fixnum=/=most-negative-
fixnum= and taught =nelisp--add2=/=nelisp--mul2= (=lisp/nelisp-jit-
strategy.el=) to signal =overflow-error= the same way =expt= already does.
That commit's own message records the limit precisely: none of it reaches
the binary this project ships.  =target/nelisp='s own top-level =+= and =*=
are native subrs baked in by an assembler-emitted dispatch table
(=scripts/nelisp-standalone-build.el=), and the actual hot path — what an
AOT-compiled =(+ a b)= lowers to — is inline =add=/=imul= machine
instructions with no overflow check at all
(=lisp/nelisp-aot-compiler.el:12091=, =--emit-arith=).  Both wrap silently.
Verified independently on this doc's own build, not just quoted from the
sibling commit: =(+ 2305843009213693951 1)= → =-2305843009213693952= on
=target/nelisp= built from this branch's tip.

*Decision*: make the checked path the default at both layers that currently
wrap — the reader's =+=/=-=/=*= dispatch (=wf_sum=/=wf_diff=/=wf_prod=) and
the AOT compiler's inline =--emit-arith= — using the exact two techniques
already proven correct and already shipping for =expt= and for
=nelisp--add2=/=nelisp--mul2= on the sibling branch: a sign-based check for
add/sub (near-free, no extra instruction class), a division round-trip for
multiply (one extra =div=, the same price =expt= already pays per iteration).
Gate the checked add/sub behind nothing — it is cheap enough to always run.
Gate the checked multiply behind the same build-time no-op mechanism
=nl-safe= already established (Doc 170 §2: "得られるもの... ビルドフラグで
no-op 化でき、リリース性能を損なわない") for numeric-heavy code that has
already proven it cannot overflow, so the default stays loud and a measured
opt-out exists for the one operation where the check is not free.

This doc feeds the bignum decision in sibling Doc 190: everywhere below that
says "signal =overflow-error='" is the interim contract until a bignum type
exists to promote into, exactly as Doc 84950ad30's own commit message framed
it for =expt=.

* §1 Problem — measured evidence

** §1.1 The constants and the elisp-layer fix (what already landed, where)

=origin/feat/stdlib-hooks-map-fixnum= (commit =84950ad30=, based on this
project's =06ed9bd3a=, *not* merged into =feat/native-observability= or
=main= as of this doc) bound the two Emacs-parity fixnum-range constants and
completed =nelisp--add2=/=nelisp--sub2=/=nelisp--mul2=:

- =most-positive-fixnum= = =2305843009213693951= (=2^61 - 1=),
  =most-negative-fixnum= = =-2305843009213693952= (=-2^61=) — Emacs's own
  61-bit-magnitude, 62-bit-signed range on a 64-bit host, confirmed bit for
  bit against Emacs 30.1 by that commit.  Independently reproduced on this
  doc's own build without even needing the constants bound: =(+
  2305843009213693951 1)= → =-2305843009213693952= directly, on
  =target/nelisp= built at this branch's tip.
- =lisp/nelisp-jit-strategy.el:582-607= (=nelisp--add2=): computes the raw
  i64 sum via =nl-jit-call-i64-i64 "nelisp_jit_add2"=, then signals
  =overflow-error= exactly when A and B share a sign and the sum's sign
  differs from theirs — the classic branchless-detectable signed-overflow
  test, correct because two already-in-range fixnums (bounded by =±2^62=)
  can never register-overflow a genuine 64-bit add; the wrap only happens
  when the sum is later narrowed back into the fixnum range.
- =lisp/nelisp-jit-strategy.el:609-620= (=nelisp--mul2=): same technique
  =expt= already used — compute the raw product, then signal
  =overflow-error= when =(/= b 0)= and =(/= (/ prod b) a)=, i.e. the product
  does not divide back out to the original operand.

** §1.2 The measured limit, in the sibling commit's own words

Quoting the comment now sitting above =nelisp--add2= in that branch
(=lisp/nelisp-jit-strategy.el=, the "MEASURED LIMIT" block), because it is
this doc's problem statement, not paraphrase:

#+begin_quote
the shipped =target/nelisp= standalone reader binary's top-level =+= and =*=
are NATIVE subrs baked in by the assembler-emitted "applyfn" core unit —
=(symbol-function '+)= there is =#<subr +>=, not this file's =defun=, and
that build does not even link =lisp/nelisp-jit-strategy.el= as one of its
units... So this fix does NOT make the actual =nelisp= binary's =(*
100000000000 100000000000)= or =(+ most-positive-fixnum 1)= signal — both
still wrap silently in every build verified against.
#+end_quote

Independently re-confirmed on this doc's own build (=target/nelisp=, this
branch, 20 s build via =make standalone-reader=):

#+begin_src text
(+ 2305843009213693951 1)                      -> -2305843009213693952
(* 100000000000 100000000000)                  -> 1864712049423024128
(symbol-function '+)                            -> #<subr +>
(symbol-function 'mod)                          -> #[(a b) (...) nil]   ; a closure
(symbol-function 'expt)                         -> #[(b e) (...overflow-error...) nil]  ; a closure
#+end_src

=mod= and =expt= come from the prelude's elisp on this same binary (their
=symbol-function= is a closure, not a subr) — which is exactly why =expt=
overflow was already loud before the sibling branch's change, and why a fix
applied only at the =nelisp-jit-strategy.el= layer cannot reach =+=/=*=
themselves: that file is not a build unit of the shipped reader.

** §1.3 Where the two arms that actually run live

Two independent code paths produce the =+=/=-=/=*= a user or a compiled
program actually observes, and neither checks anything today.

*** §1.3.1 The reader's own =+=/=-=/=*= (interpreted / REPL / =--load= path)

=scripts/nelisp-standalone-build.el:3536-3561=
(=nelisp-standalone--applyfn-dispatch-table=), the pure-elisp source the AOT
self-host process compiles into the "applyfn" dispatch unit baked into
=target/nelisp=:

#+begin_src elisp
((:u8 "+") . (... (wf_write_int out (wf_sum args 0)) ...))
((:u8 "-") . (... (wf_write_int out (wf_diff args)) ...))
((:u8 "*") . (... (wf_write_int out (wf_prod args 1)) ...))
#+end_src

=wf_sum=/=wf_prod= (=scripts/nelisp-standalone-build.el:4729-4736=) and
=wf_diff=/=wf_subtail= (=:4763-4771=) fold over the argument list with plain
=(+ acc v)=/=(* acc v)=/=(- acc v)= — at this level "=+=" is a *compiler
intrinsic* (this whole file is AOT-compiled source, not interpreted), so it
lowers straight to a raw i64 machine add/multiply with no tag-range check,
then =wf_write_int= repacks the raw i64 into a tagged fixnum, which is where
the silent narrowing-wrap actually happens.  This is the code that answers
=(+ most-positive-fixnum 1)= for every caller of the shipped binary's
top-level =+=.

*** §1.3.2 The AOT hot path (what compiled user code's =(+ a b)= becomes)

=lisp/nelisp-aot-compiler.el:12091= (=nelisp-aot-compiler--emit-arith=) is
the code every AOT-compiled Elisp =+=/=-=/=*=/=logior=/=logand=/=logxor=
form actually lowers to.  x86_64 (=:12126-12130=):

#+begin_src elisp
((eq op '+) (nelisp-asm-x86_64-add-reg-reg buf 'rax 'r10))
((eq op '-) (nelisp-asm-x86_64-sub-reg-reg buf 'rax 'r10))
((eq op '*) (nelisp-aot-compiler--imul-reg-reg buf 'rax 'r10))
#+end_src

aarch64 (=:12103-12105=) is the same shape: bare =ADD=/=SUB=/=MUL=
register-register instructions, no post-op check.  This is not a
theoretical hot path — it is the *literal same mechanism* that builds
=nelisp_jit_add2=/=nelisp_jit_mul2= themselves: =lisp/nelisp-cc-jit-
arith.el:51-64= defines them as =(defun nelisp_jit_add2 (a b) (+ a b))= /
=(defun nelisp_jit_mul2 (a b) (* a b))=, documented in that file's own
comment as "wrapping i64 add... x86_64 ADD already wraps on 2's-complement
overflow" — AOT-compiled through this exact =--emit-arith= path into
=nelisp_jit_add2.o=/=nelisp_jit_mul2.o=
(=scripts/compile-elisp-objects.el:333,339=), which every AOT-compiled
program's arithmetic and =nelisp-jit-strategy.el='s own
=nl-jit-call-i64-i64= bridge call into.  Fixing =--emit-arith= fixes both
this hot path *and* the leaf trampolines in one place, since the trampolines
are themselves output of this codegen.

** §1.4 The existing overflow-error contract to match

=scripts/nelisp-stdlib-prelude.el:2026= (=expt=), the precedent both the
elisp-layer fix and this doc's native-layer fix reuse:

#+begin_src elisp
(let ((next (* r b)))
  (when (and (/= b 0) (/= (/ next b) r))
    (signal 'overflow-error nil))
  (setq r next))
#+end_src

=overflow-error= is a real, already-signalled condition in this runtime for
one operation.  The gap this doc closes is that =+=/=-=/=*= do not honor the
same contract their sibling =expt= already does.

* §2 Decided direction

Checked by default at both layers in §1.3, using the two techniques already
proven in §1.1 — not new techniques, just moved to where the shipped binary
and the AOT hot path actually execute:

1. *Add/subtract*: the sign-based check
   (=nelisp--add2='s technique, §1.1) costs one register compare and one
   conditional branch beyond the existing =add=/=sub= — no division, no
   memory access, no allocation.  Always on, no build-flag escape hatch,
   because the cost is in the same order of magnitude as the operation it
   guards.
2. *Multiply*: the division round-trip (=expt='s and =nelisp--mul2='s
   technique, §1.1) costs one =div= beyond the existing =imul= — division is
   materially more expensive than the multiply it is checking (tens of
   cycles vs. low single digits on x86_64), so unlike add/subtract this is
   *not* free.  Default on (matching the "loud by default" contract every
   other completion in this codebase has chosen — see §7.1's precedent
   list), with the same build-flag no-op escape =nl-safe= already
   established (Doc 170 §2) for a caller that has already measured its own
   hot loop cannot overflow and wants the unchecked =imul= back.
3. *Divergence from Emacs is intentional and documented, not a bug*: Emacs's
   own =+=/=*= never signal on fixnum overflow — they silently promote to a
   bignum.  This runtime has no bignums (Doc 190, sibling), so the honest
   choices are "silent wrong answer" or "loud and different from Emacs."
   =expt= already made this call; this doc extends it to =+=/=-=/=*=,
   recorded in =docs/emacs-compat-table.txt= as a =shared-shadowing= entry
   with a divergence note, the same pattern used for =add-hook='s =LOCAL=
   argument in the sibling hooks/map.el completion.

* §3 Phased plan with costs

Effort estimates are engineer-days for a codex implementer following this
doc; each phase produces a build and a gate report, no phase lands with an
untested arm.

** P0 — Reader path: =wf_sum=/=wf_diff=/=wf_prod= (0.5–1 d)

Add the sign check to =wf_sum='s fold and =wf_diff='s tail-subtract, and the
division round-trip to =wf_prod='s fold
(=scripts/nelisp-standalone-build.el:4729-4771=), signalling
=overflow-error= through the same =(:lit ...)= convention the dispatch table
already uses for other error paths (cf. =bf_wrong_type_number_or_marker=,
already called by the =+=/=-=/=*= entries at §1.3.1 for the float-mismatch
case — the overflow signal reuses that existing error-propagation channel,
not a new one).

*Exit*: rebuild =target/nelisp=; =(+ most-positive-fixnum 1)= and =(*
100000000000 100000000000)= both signal =overflow-error= instead of
returning a wrapped value; =(+ 1 2)=, =(* 6 7)=, and every existing
arithmetic-touching ERT case in =test/nelisp-eval-test.el= and the =make
test= suite still pass unchanged (the check only fires within one ULP of the
boundary, never on an in-range result).

** P1 — AOT hot path: =--emit-arith= (1.5–2.5 d)

Extend =nelisp-aot-compiler--emit-arith= (=lisp/nelisp-aot-compiler.el:12091=)
for =+=/=-= with the sign-check sequence (compare-and-branch to a shared
overflow-landing label that calls the existing AOT error-signal machinery —
the same "signal a Lisp error from compiled code" path non-local exits
already use, per Doc 171 §2.3's =aot-push-catch/unwind=) on both x86_64 and
aarch64; for =*=, the division round-trip, same landing.  =nelisp_jit_add2=/
=nelisp_jit_mul2= (=lisp/nelisp-cc-jit-arith.el:51-64=) inherit the checked
behaviour automatically once =--emit-arith= changes, since they compile
*through* it — no separate edit needed there, which is also why a
regression here breaks both the leaf trampolines and every AOT-compiled
program's inline arithmetic at once (see §5's mutation row).

*Exit*: an AOT-compiled test program containing =(+ most-positive-fixnum
1)=/=(* 100000000000 100000000000)= signals =overflow-error= when executed
as a native artifact (mirrors Doc 164's exit-criterion shape: compile,
execute, assert on the *emitted binary*, not the compiler's internal IR);
the existing =bench-aot-tco= and =nelisp-aot-compiler-test.el= arithmetic
cases still pass byte-for-byte on in-range values.

** P2 — Build-flag opt-out for the multiply check only (0.5 d)

Wire the =*='s division round-trip (both P0 and P1 sites) behind the same
mechanism =nl-safe= already uses to no-op its checks at build time (Doc 170
§2), so a caller with a measured hot multiply loop can drop back to the raw
=imul=.  Add/subtract stay unconditionally checked — §2 already established
their cost does not justify an escape hatch.

*Exit*: the flag flips =*='s behaviour on a small compiled probe (checked →
signals at the boundary; flagged-off → wraps, matching pre-Doc-187
behaviour byte-for-byte); default build state is checked (flag *off* means
"no-op the check", not "opt in to it" — matching =nl-safe='s own default
direction).

** P3 — Cost measurement (0.5–1 d)

Use =tools/ai/bench-compare.sh='s two-arm, three-guard methodology (slope /
drift / identity, per =tools/ai/README.md=) rather than a bare before/after
timing, since that is this project's own standard for a number anyone would
trust: base arm = pre-P0/P1 unchecked =+=/=*= in a tight loop (=n=0= vs.
=n=N= to subtract start-up, base arm run twice at =n=N= to catch drift,
digest-checked artifact identity), candidate arm = the checked build.
Follows the same shape as the existing =bench-aot-tco= gate (Doc 171 G4),
which already benches one native-artifact arithmetic path against a
hand-written control.

*Exit*: a =bench-compare.sh= report for add-heavy and multiply-heavy probes,
each showing a ratio, not a hand-typed percentage; if the multiply ratio is
large enough to matter for realistic AOT-compiled workloads (no threshold
guessed here — measure first, per AI.md rule 3, "a measurement is invalid
unless its baseline is [checked]"), P2's opt-out is the documented mitigation
already in place, not a new one to design under time pressure.

* §4 Verification design

** §4.1 Against-the-bug

The bug this doc closes is exactly reproducible today (§1.2) and has an
unambiguous post-fix answer:

| form | today (measured) | after P0+P1 |
|---|---|---|
| =(+ most-positive-fixnum 1)= | =-2305843009213693952= (wraps) | signals =overflow-error= |
| =(* 100000000000 100000000000)= | =1864712049423024128= (wraps) | signals =overflow-error= |
| =(+ 1 2)=, =(* 6 7)=, in-range cases | correct | unchanged |
| =(expt 2 100)= | already signals =overflow-error= (unchanged reference) | unchanged |

A new ERT case in =test/nelisp-eval-test.el= (P0) and a new AOT e2e smoke
(P1, in the =standalone-reader-*-smoke= family per §3's exit criteria)
assert the left column no longer reproduces once each phase ships.

** §4.2 Parity forms — and the one deliberate non-parity

Every other case in this doc's scope should be run against real Emacs 30.1
via the =nelisp-parity-probe= skill and *agree*: in-range add/subtract/
multiply, negative operands, zero, the exact fixnum boundary minus one.  The
overflow case itself is the single form that must *diverge* by design (§2.3)
— Emacs promotes to a bignum and returns a correct large integer; this
runtime signals.  That divergence is recorded in
=docs/emacs-compat-table.txt= (regenerate via =make emacs-compat-table=
after landing) with a note, not silently left as an unexplained
"shared-shadowing" row — matching the =LOCAL= divergence note the hooks/map.el
sibling completion already set the precedent for.

* §5 Open questions

- *Where does the P1 overflow signal actually land in AOT-compiled code?*
  §3's P1 sketches "call the existing non-local-exit signal machinery," but
  the exact landing-label wiring for a *newly introduced* signal site (as
  opposed to an existing =condition-case=/=throw= desugar target) needs a
  spike against Doc 171 §4's call-lowering description before P1's estimate
  is trustworthy.
- *Does the P2 build flag need to be per-call-site or whole-build?* =nl-safe='s
  precedent (Doc 170) is whole-build. A per-hot-loop opt-out (e.g. a
  =declare= on a =defun=) would be finer-grained but is new surface this doc
  does not scope.
- *Bitwise ops* (=logior=/=logand=/=logxor=) share =--emit-arith='s dispatch
  but cannot overflow a fixnum the way add/multiply can (the result is
  always a subset of the input bits) — confirm no check is needed there
  before P1 touches those arms, rather than assuming.
- *Does =nelisp--sub2= need the same sign check as =nelisp--add2=, or is
  subtraction's overflow case actually a disguised add (=a - b = a + (-b)=)
  already covered once =-b= itself is range-checked?*
  =lisp/nelisp-jit-strategy.el:600-607= currently has *no* overflow check on
  =nelisp--sub2= at all on the sibling branch — worth confirming this is a
  real gap there too (=(- most-negative-fixnum 1)= should also signal) before
  assuming §3's "extend =+=/=-=" scope is symmetric with what already landed
  upstream of this doc.
