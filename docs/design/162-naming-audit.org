#+TITLE: 162 — Naming Audit: Concurrency-Sounding Names on Single-Thread Machinery
#+STATUS: DRAFT (investigation + proposal only, no renames applied)

* Motivation

While debugging the Doc 152 mid-form GC work this week, a reasonable reader
looking at ~nl_gc_loop_ctx~ / ~nl_gc_collect_published~ hypothesized a
*multithreading* mechanism (safepoints and cross-thread publication are
textbook concurrent-GC vocabulary — JVM/Go-style stop-the-world safepoints,
publish/subscribe between threads). The actual code is a *single-thread*,
mid-form GC: a context stack the collector reads back from at a loop
back-edge, inside one interpreter, one OS thread, no shared memory between
threads at all.

The risk is compounded by the fact that this codebase's Makefile and
~lisp/nelisp-cc-atomic-raw-mem.el~ *do* contain genuine concurrency
machinery elsewhere (an actual actor runtime bench, a real
clone(2)+atomics multi-threaded self-host test, `fork(2)`-based parallel
compilation, and hardware `SeqCst` atomic refcount ops used because the
standalone tool really can run multiple OS threads/processes during
parallel builds — see `scripts/nelisp-standalone-build.el:4566`). Those
uses are legitimately named. That real concurrency vocabulary living a few
files away from purely single-thread interpreter/GC internals is exactly
what makes misleading names in the latter dangerous: the reader has no
local signal to tell the two apart, and correctly-named neighbors lend
false credibility to the incorrect hypothesis.

This document inventories every case of that pattern found in the
standalone-reader codebase, confirms or refutes each by reading the
implementation, and proposes replacement names. **No renames are applied
in this branch** — this is audit-only, per task scope.

* Scope swept

- ~scripts/nelisp-standalone-build.el~ (15,618 lines)
- ~lisp/nelisp-cc-*.el~ (188 files), ~lisp/nelisp-lexframe.el~,
  ~lisp/nelisp-stdlib-*.el~ (20 files), ~lisp/nelisp-aot-compiler.el~
  (17,217 lines), ~src/nelisp-cc.el~ (2,097 lines)
- Builtin surface (~nelisp--*~ names reachable from the reader),
  ~Makefile~ targets, ~lisp/nelisp-cli.el~ flags

Note: ~packages/nelisp-actor~, ~packages/nelisp-jit~ (the older
host-Emacs-hosted NeLisp interpreter's *real* runtime JIT), and the
Makefile's `actor-bench` / `soak-worker` / `standalone-selfhost-mt-test` /
`standalone-parallel-compile-test` targets were checked and are **correctly
named** — they describe genuine concurrency (real OS threads, `fork(2)`
workers, an actual actor mailbox runtime). They are out of scope for
renaming and are called out only as contrast/context above.

* Recommended rename batch plan

Given the P1 findings are the highest-value fix (they are the ones that
actively produce wrong mental models, as this week demonstrated) and the
P2 findings are either high-blast-radius (mirror, jit_) or user-facing
builtin surface (gc-diag), the recommended order is:

1. **Batch 1 (P1, source-only, no ABI/binary-symbol impact) — do first:**
   - ~nl_gc_collect_published~ family → ~nl_gc_collect_from_recorded_roots~
     / ~nl_gc_mark_recorded_*~ (item 3). These are DSL-internal defun names
     baked at AOT-compile time, not Rust-linked symbols — pure `sed`
     rename inside ~scripts/nelisp-standalone-build.el~ and
     ~scripts/nelisp-flat-arena-probe.el~.
   - Add a one-paragraph doc-caveat (no rename) to ~nl_val_clone_into~'s
     docstring clarifying the shallow-rebox fast path (item 4) — already
     mostly done by commit ~0f66cb1c~'s own comment; just needs the public
     C-ABI docstring at the top of ~lisp/nelisp-cc-sexp-clone-into.el~ and
     ~lisp/nelisp-cc-val-load.el~ updated to stop calling the whole family
     "clone" unconditionally.

2. **Batch 2 (P1, linked BSS symbol — needs full rebuild to verify):**
   - ~nl_gc_loop_ctx~ → ~nl_gc_loop_ctx~, ~nl_gc_midform_collect~ →
     ~nl_gc_midform_collect~ (items 1-2). Mechanical `sed -i
     's/nl_gc_loop_ctx/nl_gc_loop_ctx/g; s/nl_gc_midform_collect/nl_gc_midform_collect/g'`
     across ~scripts/nelisp-standalone-build.el~ and
     ~lisp/nelisp-cc-sf-while.el~, then rebuild — this symbol is emitted via
     ~nelisp-link-symbol~ so the *name* only matters for source
     readability/gdb-session friendliness, not ABI compat with anything
     external (nothing outside this repo links against it by name).

3. **Batch 3 (P2, user-facing builtin — needs a deprecation-style path):**
   - ~nelisp--gc-diag~ → keep the old name as an alias for one release,
     add ~nelisp--interp-diag~ as the new primary name, migrate the 3
     docs/design references and the test suite call sites, then drop the
     alias. Do NOT silently rename a builtin callable from user NeLisp
     source without a grace period.

4. **Batch 4 (P2, cross-repo/high-blast-radius — separate dedicated
   effort, not part of a quick sed pass):**
   - ~wf_ht_*~ → ~nl_ht_*~ (mechanical, source-only, moderate size).
   - "mirror" family: recommend documentation-only fix, not a rename,
     because it mirrors (no pun intended) a Rust-side name 1:1 and a
     one-sided rename would desync the two codebases' vocabularies.
   - ~jit_~/~nelisp_jit_*~ in ~lisp/nelisp-cc-jit-*.el~: recommend a
     *joint* Rust+elisp rename in a dedicated Doc, since these are
     linked object-file exported symbols consumed by exact name from
     `build.rs`/`unified_fn_ptr`. Out of scope for a mechanical elisp-only
     sed batch.

**Verification for any batch that touches Batches 1-3 (source-only or
linked-symbol renames):** full standalone build
(~make standalone-reader~), ~make standalone-reader-test~, all
~standalone-reader-*-smoke~ targets (load/fmt/prelude-equal/
nested-backquote/derived-mode/process/realrt/repl/prelude/ffi/tls/
chunk-growth), plus the AOT-compiler and CC test suites
(~make standalone-eval-test~, existing ERT suites under ~test/~ that cover
~nelisp-cc-*~ and ~nelisp-aot-compiler.el~). Diff before/after byte
identity on a fixed input corpus (the existing 60-file org replay probe
used in commit ~0f66cb1c~ is a good template) to confirm zero behavior
change from a pure rename.
