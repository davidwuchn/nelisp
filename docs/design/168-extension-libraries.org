* 1. 目的

NeLisp 上で動作する **opt-in の言語拡張ライブラリ群** を設計する。目的は2つ。

1. Emacs Lisp の言語的欠陥（TCO 不在、名前空間不在、網羅性検査不在、
   エラー処理の弱さ、条件システムの貧弱さ）を補完する
2. ランタイム実装層に残る unsafe 面（生ポインタ、syscall-direct、
   frame-alloc、可変長引数）に、Rust 的な安全境界を与える

* 2. 非目標 (Non-goals)

- **素の Elisp の意味論を変更しない。** 本ライブラリ群を読み込んでいない
  コードの挙動は一切変わらない
- **Emacs 互換性の主張を弱めない。** 拡張は全て別パッケージ、opt-in
- 完全な Rust 借用検査器の再現 — 静的健全性は限定範囲でのみ主張する
- 新方言の定義 — あくまで Elisp のライブラリであり、S 式の読み方は変えない

* 3. 中核となる設計原則

** 3.1 三層の仕分け (LOCKED)

すべての機能案を、実装に必要な最も浅い層に配置する。
ライブラリで済むものをランタイム改造にしない。

| 層 | 実装手段                     | 影響範囲       | 撤回コスト |
|----+------------------------------+----------------+------------|
| L1 | マクロ + 関数のみ            | パッケージ内   | 低         |
| L2 | AOT/JIT コンパイラパス       | コンパイル単位 | 中         |
| L3 | 評価器・リーダーの拡張       | 処理系全体     | 高         |

*規律*: L2/L3 に着手するのは、同等機能の L1 版を出荷して実使用データを
得た後に限る。設計段階で L3 が必要と判断した機能は、Doc 90
(ideas-backlog) に送り、本ドキュメントのスコープから外す。

** 3.2 動的検査を先、静的検査を後 (LOCKED)

安全機能は、まず実行時チェックとして実装する。理由:

1. 実装コストが桁で小さく、今週書ける
2. 実際の違反データが取れる。静的検査器の設計はそのデータを見てから行う
3. API 構文を先に固定できるため、後から同じ構文の上に静的パスを載せられる
4. ビルドフラグで no-op 化でき、リリース性能を損なわない

TypeScript の =--strict= 段階導入、Racket の contract と同じ戦略。

** 3.3 検査器は独立パッケージに置く (LOCKED)

マクロ展開時の静的検査は =nl-check= に分離し、機能パッケージからは
依存しない。検査を外せる状態を常に保つ。

** 3.4 健全性の主張範囲を明示する

=eval= と実行時再定義がある以上、全プログラムに対する健全性は主張しない。
ファイル単位の宣言でスコープを切る。

#+begin_src elisp
;;; -*- lexical-binding: t -*-
(nl-strict t)   ; このファイル内でのみ展開時検査を有効化
#+end_src

境界を越える値は、契約 (Doc 170 §7) による動的チェックで守る。

* 4. パッケージ構成

既存の =packages/<name>/{src,test,README.org}= 規約に従う。

#+begin_example
packages/
├── nl-prelude/     # Result, Option, ADT, match, gensym, recur   [Doc 169]
├── nl-condition/   # handler-bind, restart-case, invoke-restart  [Doc 169]
├── nl-safe/        # cell/borrow, ptr, resource, drop            [Doc 170]
├── nl-contract/    # 境界契約と責任所在の報告                    [Doc 170]
└── nl-check/       # 展開時検査パス（独立ツール）                [Doc 170]
#+end_example

** 4.1 依存グラフ

#+begin_example
nl-prelude  ←── nl-safe  ←── nl-contract
     ↑              ↑
nl-condition        │
                    │
nl-check ───────────┘   （検査のみ。実行時には不要）
#+end_example

- =nl-prelude= は他のどのパッケージにも依存しない
- =nl-check= はどのパッケージからも依存されない（一方向）
- 循環依存を作らないこと。これが崩れると検査を外せなくなる

** 4.2 命名規約

| 対象                     | 規約                | 例                        |
|--------------------------+---------------------+---------------------------|
| 公開シンボル             | =nl-= プレフィックス | =nl-ok=, =nl-with-borrow= |
| 内部シンボル             | =nl--=              | =nl--cell-check=          |
| パッケージ固有の内部     | =nl-safe--=         | =nl-safe--ptr-validate=   |
| 展開時にのみ使うマクロ変数 | =nl--g-=            | =nl--g-tmp=               |

Elisp に名前空間がないため、プレフィックスは規約で守る。名前空間の
リーダーサポート（L3）は本スコープ外（Doc 90 送り）。

* 5. ロードマップ

** Phase 1 — nl-prelude v0.1 (最初の出荷単位)

スコープを Result / Option / =nl-?= のみに絞る。数百行。

- 受け入れ条件:
  - ERT 40 件以上、全 green
  - =target/nelisp= 上で Emacs なしで動作
  - README.org に使用例
  - =packages/nelisp-json= に続く2例目の分割実例となること

** Phase 2 — 並行して2本

*** 2a. nl-prelude v0.2 — ADT + 網羅性検査
展開時解析の練習。対象が閉じており =eval= の影響を受けにくいため、
検査器の書き方を安全に習得できる。

*** 2b. 検証アロケータ（ランタイム側、ライブラリ外）
redzone / poison / 世代タグ。投入労力あたりのバグ検出数が最大。
Doc 170 §5 に詳細。

** Phase 3 — nl-safe v0.1
動的借用 (=nl-cell=) と fat pointer。Phase 2b で得た違反データを設計入力とする。

** Phase 4 — nl-condition v0.1
restart system。Elisp 界隈全体に価値がある部分。

** Phase 5 — L2: 末尾呼び出し最適化
AOT コンパイラへのパス追加。NeLisp の最大の差別化要素。
Emacs 意味論を変えない（スタックが伸びなくなるだけ）ため互換性リスクなし。

** Phase 6 — 静的線形性検査 (nl-check)
Phase 3 の実使用データを見てから設計に着手する。
*着手判断のゲート*: 動的検査が捕捉した違反のうち、静的に判定可能な
ものが 50% を超えていること。下回る場合は Phase 6 を中止する。

* 6. 品質ゲート

各パッケージの出荷条件（既存 CI 規約に合わせる）。

| ゲート                  | 条件                                        |
|-------------------------+---------------------------------------------|
| ERT                     | unexpected 0 件                             |
| standalone 実行         | =target/nelisp= 上で全テスト green          |
| 非侵襲性                | 未ロード時に既存 3604 件のテスト結果が不変  |
| 無効化                  | ビルドフラグで検査を no-op 化した状態でも動作 |
| ドキュメント            | README.org に動機・API・非目標              |

*非侵襲性ゲートが最重要*。これが NeLisp の互換性主張を守る。

* 7. リスクと対策

| リスク                             | 影響 | 対策                                       |
|------------------------------------+------+--------------------------------------------|
| スコープクリープで未完成の柱が増える | 高   | Phase 1 を数百行に絞り、単体で出荷して区切る |
| 拡張が増え Emacs 互換の主張が濁る   | 高   | opt-in 別パッケージ、非侵襲性ゲート          |
| 検査器が本体に癒着し外せなくなる    | 中   | nl-check の一方向依存を CI で検証            |
| 動的検査の性能コスト                | 中   | ビルドフラグで no-op 化、ホットパスで計測    |
| 静的検査に投資しても回収できない    | 中   | Phase 6 に定量的な着手ゲートを設定           |

*最大のリスクはスコープクリープ*。Layer 2 (Emacs 意味論) と Layer 3
(GUI) が未完のまま、さらに2本の柱を立てる構図であることを常に意識する。
Phase 1 を独立に出荷して一度手を止め、継続判断を行うこと。
