#+TITLE: Doc 187 — arithmetic overflow consistency at the native layer
#+AUTHOR: nelisp / nelisp-emacs (design: Claude Opus 5 + zawatton)
#+DATE: 2026-08-22
#+STATUS: DRAFT — design only, no implementation in this doc.

* §0 TL;DR

The elisp layer now has honest fixnum-overflow behaviour: =expt= has
signalled =overflow-error= on wraparound for a long time (division
round-trip after the multiply), and =nelisp--add2=/=nelisp--mul2= in
=lisp/nelisp-jit-strategy.el= gained the same discipline this session on
=origin/feat/stdlib-hooks-map-fixnum= (commit =84950ad30=, not yet merged
to =main= or to this doc's base branch =feat/native-observability=).  But
the shipped =target/nelisp= standalone binary's own top-level =+= and
=*= are native subrs generated by a *different* code path — the
=nelisp-standalone--applyfn-dispatch-table= in
=scripts/nelisp-standalone-build.el= — and that path still wraps
silently.  Re-verified directly on this clone, independent of the
sibling branch and independent of last session's commit message:

#+begin_src elisp
(defconst most-positive-fixnum 2305843009213693951)
(defconst most-negative-fixnum -2305843009213693952)
(symbol-function '+)                       ; => #<subr +>  (native, not elisp)
(+ most-positive-fixnum 1)                 ; => -2305843009213693952 (== most-negative-fixnum)
(* 100000000000 100000000000)              ; => 1864712049423024128  (garbage, true value ~1e22)
#+end_src

This doc designs the fix at the layer that actually ships: the
=applyfn= dispatch table's =wf_sum=/=wf_prod= fold helpers
(=scripts/nelisp-standalone-build.el:4729-4736=, reached from the =+=/=*=
table entries at =:3535=/=:3556=) and the AOT compiler's inline
=+=/=-=/=*= codegen (=nelisp-aot-compiler--emit-arith=,
=lisp/nelisp-aot-compiler.el:12091=), which is both the hot path for
*every* AOT-compiled program's arithmetic and the source that builds
=nelisp_jit_add2=/=nelisp_jit_mul2= themselves
(=lisp/nelisp-cc-jit-arith.el:52,63=).  Recommendation: apply the exact
technique already proven at the elisp layer — a division round-trip for
=*=, a sign-based check for =+= — at both of these native sites, gated
so the check costs one comparison and (almost always) zero branches
taken per operation; measure the real cost with
=tools/ai/bench-compare.sh= rather than assume it, because both sites
are genuinely hot.

* §1 Problem — measured evidence

** §1.1 The elisp layer is already fixed, and already knows its own limit

=origin/feat/stdlib-hooks-map-fixnum= commit =84950ad30= (2026-08-22,
not merged) added =most-positive-fixnum=/=most-negative-fixnum= as real
constants and completed =nelisp--add2=/=nelisp--mul2= in
=lisp/nelisp-jit-strategy.el:582-620=:

#+begin_src elisp
(fset 'nelisp--add2
      (lambda (a b)
        (if (nelisp--ref-eq (type-of a) 'integer)
            (if (nelisp--ref-eq (type-of b) 'integer)
                (let ((sum (nl-jit-call-i64-i64 "nelisp_jit_add2" a b)))
                  (if (or (and (>= a 0) (>= b 0) (< sum 0))
                          (and (< a 0) (< b 0) (>= sum 0)))
                      (signal 'overflow-error nil)
                    sum))
              (nelisp--add2-float a b))
          (nelisp--add2-float a b))))

(fset 'nelisp--mul2
      (lambda (a b)
        (if (nelisp--ref-eq (type-of a) 'integer)
            (if (nelisp--ref-eq (type-of b) 'integer)
                (let ((prod (nl-jit-call-i64-i64 "nelisp_jit_mul2" a b)))
                  (if (and (/= b 0) (/= (/ prod b) a))
                      (signal 'overflow-error nil)
                    prod))
              (nelisp--mul2-float a b))
          (nelisp--mul2-float a b))))
#+end_src

Both checks are the same techniques =expt= already used
(=scripts/nelisp-stdlib-prelude.el:2026-2037=):

#+begin_src elisp
(defun expt (b e)
  ...
  (let ((r 1) (i 0))
    (while (< i e)
      (let ((next (* r b)))
        (when (and (/= b 0) (/= (/ next b) r))
          (signal 'overflow-error nil))
        (setq r next))
      (setq i (1+ i)))
    r))
#+end_src

The =+= check is sound because two operands already in fixnum range
(bounded by ±2^61) can never overflow a genuine 64-bit add — the wrap,
when it happens, is detectable purely from the three signs.  The =*=
check is the classic "does it divide back out" round-trip, correct
whenever =b ≠ 0= (and =b = 0= can never overflow a product).

That same commit's own long comment (reproduced here because it is the
single most load-bearing fact in this doc, and re-verified independently
below rather than trusted) is explicit that this fix does *not* reach
the shipped binary:

#+begin_quote
the shipped =target/nelisp= standalone reader binary's own top-level
=+=/=*= are NATIVE subrs from the assembler-emitted "applyfn" core unit
(=(symbol-function '+)= there is =#<subr +>=, not an elisp =defun=), and
that build does not even link =lisp/nelisp-jit-strategy.el= as one of
its units [...] So this fix does NOT make the actual =nelisp= binary's
=(* 100000000000 100000000000)= or =(+ most-positive-fixnum 1)= signal;
both still wrap silently there.
#+end_quote

** §1.3 Where the native =+=/=*= actually come from

=scripts/nelisp-standalone-build.el:3535= (=nelisp-standalone--applyfn-dispatch-table=)
dispatches =+=/=*= to fold helpers:

#+begin_src elisp
((:u8 "+") . (let* ((f (wf_any_float args))) ...
                (wf_write_int out (wf_sum args 0))))
((:u8 "*") . (let* ((f (wf_any_float args))) ...
                (wf_write_int out (wf_prod args 1))))
#+end_src

=wf_sum=/=wf_prod= (=:4729-4736=) are a plain recursive fold with *no*
overflow check at all — not even the i64-hardware-wrap kind =expt='s
technique detects:

#+begin_src elisp
(defun wf_sum (list_ptr acc)
  (if (= (ptr-read-u64 list_ptr 0) 7)
      (let* ((car_ptr (nl_cons_car_ptr list_ptr)) (v (ptr-read-u64 car_ptr 8)))
        (wf_sum (nl_cons_cdr_ptr list_ptr) (+ acc v))) acc))
(defun wf_prod (list_ptr acc)
  (if (= (ptr-read-u64 list_ptr 0) 7)
      (let* ((car_ptr (nl_cons_car_ptr list_ptr)) (v (ptr-read-u64 car_ptr 8)))
        (wf_prod (nl_cons_cdr_ptr list_ptr) (* acc v))) acc))
#+end_src

This file is itself compiled through the AOT pipeline (it is how
=target/nelisp= is built at all), so the =(+ acc v)= inside =wf_sum= is
not interpreted — it goes through the exact same codegen as any other
AOT arithmetic, which is §1.4.

** §1.4 The AOT hot path: every compiled =+=/=-=/=*= in every program

=nelisp-aot-compiler--emit-arith= (=lisp/nelisp-aot-compiler.el:12091=)
is what any AOT-compiled Elisp form's =(+ A B)= actually lowers to. On
x86_64 (=:12127-12128=) it is a bare =add rax, r10= / an =imul=; on
aarch64 (=:12102-12104=) a bare =add x0, x0, x9= / =sub= / =mul=.  No
overflow check on either architecture, by design — this is meant to be
the cheapest possible integer op.

This is the *same* codegen path that builds =nelisp_jit_add2=/
=nelisp_jit_mul2= themselves: =lisp/nelisp-cc-jit-arith.el:52,63=

#+begin_src elisp
(defconst nelisp-cc-jit-arith-add2--source
  '(defun nelisp_jit_add2 (a b) (+ a b))
  "AOT source for `nl_jit_arith_add2' — wrapping i64 add.
Emits `add rax, r10' inline (= 3 bytes).")
(defconst nelisp-cc-jit-arith-mul2--source
  '(defun nelisp_jit_mul2 (a b) (* a b))
  "AOT source for `nl_jit_arith_mul2' — wrapping i64 multiply.
Emits `imul rax, r10' (= 4 bytes).")
#+end_src

compiled to =nl_jit_add2.o=/=nl_jit_mul2.o= via
=scripts/compile-elisp-objects.el:333,339= and linked into the binary.
So there are, precisely, *two* native sites that need the fix, not one:
the reader's own =+=/=*= subrs (§1.3, via =wf_sum=/=wf_prod=) and the
AOT compiler's inline arithmetic emission (§1.4, via
=--emit-arith=) — and the second one is both what user programs compile
to *and* what builds the raw =nelisp_jit_add2=/=mul2= leaves that
=nelisp-jit-strategy.el='s (unshipped, in this binary) checked wrapper
calls into. Fixing only =nelisp_jit_add2= itself would not fix
=wf_sum=/=wf_prod= (a different call site entirely, not routed through
=nelisp_jit_add2=), and fixing only =wf_sum=/=wf_prod= would leave every
AOT-compiled user program's inline =+=/=*= still silently wrapping.

** §1.5 Contrast: =expt='s contract is the one honest precedent

=expt= (§1.1) is the one place in the shipped binary that is elisp, not
a native subr (=(symbol-function 'mod)= and =(symbol-function 'expt)=
are both closures/lambdas there, confirmed above for =mod=), and it
already signals =overflow-error= reliably.  This doc's job is to make
=+=/=*= match that contract, not invent a new one.

* §2 Decided direction

*Apply the same two checks — sign-based for =+=, division-round-trip for
=*= — at both native sites (§1.3 =wf_sum=/=wf_prod=, §1.4
=--emit-arith=), rather than only completing the elisp-layer
=nelisp--add2=/=nelisp--mul2= wrappers (already done, on the sibling
branch, and demonstrably insufficient because the shipped binary does
not reach them).*

Two candidate directions were weighed and rejected:

| option | why rejected |
|---|---|
| Redefine the native =+=/=*= subrs unconditionally from elisp (drop the =unless (fboundp ...)= guard so the prelude's elisp definition wins) | Pays the check for *every* fixnum add/multiply system-wide, including the interpreter's own hot loops that never come near the boundary, exactly the option the sibling commit's comment already rejected for the same reason — and does not reach =--emit-arith= at all, since AOT-compiled code does not call through the subr table. |
| Leave the native layer wrapping and document it (accept-wrap contract) | This is the honest fallback if the measured cost turns out too high (§4.3), but it is not the default: =expt= already sets the precedent that overflow is loud here, and a language where =+= silently corrupts values but =expt= does not is a worse, less learnable contract than either "always loud" or "always documented-wrap." |
| Fix only =wf_sum=/=wf_prod= (§1.3) and treat the AOT compiler's inline emission (§1.4) as future work | Rejected as incomplete: §1.4 is explicitly named in this doc's mandate as "the AOT hot path," and it is reachable by every AOT-compiled program today, not a hypothetical future consumer. |

The checked-add/checked-mul technique itself is not novel here — it is
already proven correct and already ships (in =expt=, and in the
unshipped =nelisp-jit-strategy.el= wrappers). The design work in this
doc is entirely about *where* to place it in the two hot-path
generators and how to validate the cost honestly.

* §3 Design detail

** §3.1 Fixing =wf_sum=/=wf_prod= (reader's native =+=/=*=)

=wf_sum= folds left with an accumulator; the natural insertion point is
inside the fold, so a partial sum's overflow is caught at the exact
operation that caused it (matching =expt='s per-step check, not a
whole-sum-at-the-end check that could not localize the fault):

#+begin_src text
wf_sum(list, acc):
  if list is nil: return acc
  v = car(list)
  sum = acc + v                      ; native i64 add, still wraps at hw level
  if sign(acc) == sign(v) and sign(sum) != sign(acc):
      signal-overflow()              ; new: same 3-sign test as nelisp--add2
  return wf_sum(cdr(list), sum)
#+end_src

=wf_prod= gets the division round-trip in the same position, guarded on
=v ≠ 0= exactly as =expt=/=nelisp--mul2= already do. Both checks are
expressed as the same primitive comparisons =wf_sum=/=wf_prod= already
use elsewhere in this file (=ptr-read-u64=, =<=, =(quote signal)= via
whatever this file's existing error-raise idiom is — see
=bf_wrong_type_number_or_marker= at the =+=/=*= dispatch-table entries,
§1.3, for the established "raise from inside an =applyfn= helper"
pattern to reuse rather than invent a new one).

** §3.2 Fixing =--emit-arith= (AOT inline codegen)

This is the more delicate site because it emits raw machine
instructions, not elisp. The shape (x86_64, =+= as an example):

- today: =add rax, r10= (§1.4, one instruction, three bytes).
- checked: =add rax, r10= then a signed-overflow check via the =OF=
  flag x86 already sets on the add — =jo overflow_label= (jump-if-overflow,
  two bytes) is *cheaper* than the sign-based elisp check, because the
  CPU already computed the overflow flag as a side effect of the ADD
  itself; no extra comparison is needed, only a conditional branch that
  is not taken on the overwhelmingly common path.  =imul='s two-operand
  form also sets =OF= on truncation, so =*= gets the same =jo= treatment
  with *no* division round-trip needed in the native emitter — the
  elisp-layer division check (§1.1) exists only because the elisp
  wrapper does not have hardware flags to read; codegen does.
- aarch64: =adds=/=subs= (flag-setting forms of add/sub) set the =V=
  (overflow) flag identically; =smulh=/=mul= pairs are the standard
  aarch64 signed-multiply-overflow idiom (high half of a 128-bit
  product, compared against a sign-extension of the low half) — costs
  one extra multiply instruction plus a compare, the aarch64 ISA having
  no single-instruction overflow-checked multiply.
- overflow_label lands on a runtime helper that raises exactly the
  same =overflow-error= symbol =expt= raises, so a =condition-case=
  around AOT-compiled arithmetic behaves identically whether the
  offending form was interpreted or compiled.

This is materially *cheaper* on x86_64 than the elisp-layer version:
=jo= after an =add= that already happened is one flag test, not a
three-comparison sign check. The real cost is not the check itself; it
is the branch-prediction and code-size effect of adding a conditional
jump plus an out-of-line error path to *every* arithmetic op in every
AOT-compiled hot loop, which is exactly why §4.3 insists on measuring,
not assuming, before this ships as the unconditional default.

** §3.3 Why this cannot be a compiler-elisp-level fix instead

=nelisp-aot-compiler--emit-arith= evaluates operands with
=nelisp-aot-compiler--emit-value= and combines the two OP-specific
instruction emissions (=nelisp-asm-x86_64-add-reg-reg= /
=nelisp-aot-compiler--imul-reg-reg= / arm64 equivalents) — these are
themselves thin wrappers that write instruction bytes into a buffer
(=nelisp-asm-x86_64.el=/=nelisp-asm-arm64.el=). The overflow check has
to be a *third* instruction (or two) inserted immediately after the
arithmetic op and before the result is used, plus a new out-of-line
label the emitter's existing label/fixup machinery must track through
its pass-invariance discipline (=--emit-temp-push=/=--emit-temp-pop=
already establish that push/pop must be byte-fixed for the two-pass
assembler to agree with itself — the overflow branch has the same
constraint: its size must be identical on both compiler passes, which
=jo REL8= to a fixed-size out-of-line stub already satisfies).

* §4 Phased plan with costs

Effort estimates are engineer-days for an implementer following this
doc, in the style of Doc 164 §6.

** P0 — =wf_sum=/=wf_prod= checked (0.5-1 d)

- Add the sign check inside =wf_sum='s fold and the division round-trip
  inside =wf_prod='s fold (§3.1). =wf_diff='s subtraction fold
  (=:4756-4761=) gets the equivalent subtraction check (opposite-sign
  operands, result sign matching the *subtrahend's* sign is the overflow
  case — the mirror of the addition check).
- *Exit*: rebuild =target/nelisp=; the §1.2 probe's =(+ most-positive-fixnum 1)=
  now signals =overflow-error= instead of returning
  =most-negative-fixnum=; =(* 100000000000 100000000000)= signals
  instead of returning =1864712049423024128=; every existing
  arithmetic-bearing ERT case and the =standalone-reader-*= smokes stay
  green (this is a narrowing of previously-silent-wrong behaviour, not a
  value-shape change for any in-range operation).

** P1 — =--emit-arith= checked on x86_64 (1-2 d)

- =jo=-based overflow detection after =add=/=sub=/=imul= (§3.2), routed
  to a shared out-of-line =signal 'overflow-error= stub reachable from
  every call site (one stub, not one per call site, to keep code-size
  growth to the branch instruction only).
- *Exit*: an AOT-compiled =(defun f (a b) (+ a b))= called with
  =most-positive-fixnum 1= signals =overflow-error= under
  =nelisp-aot-compile-to-object= + native execution (mirrors the
  =standalone-reader-*-smoke= exit-code-comparison pattern in
  =Makefile:182-676=); a non-overflowing AOT arithmetic benchmark
  (§4.3) shows the measured cost.

** P2 — =--emit-arith= checked on aarch64 (1-2 d)

- =adds=/=subs= flag-setting forms + the =smulh=-based multiply-overflow
  idiom (§3.2).
- *Exit*: same overflow-error assertion as P1, executed under the qemu
  aarch64 harness Doc 151 (=docs/design/151-arm64-targets.org=) already
  established for cross-architecture AOT execution testing.

** P3 (optional, gated on P1's measurement) — feature-flag the checked path

- If §4.3's measurement shows an unacceptable regression on an
  arithmetic-dominated benchmark, wrap the checked emission behind an
  AOT compiler flag (default ON per §2's decision, OFF available),
  rather than reverting the fix outright — the sibling commit's
  documented-wrap fallback (§2, option 2) becomes the OFF-state
  contract, spelled out in =docs/runtime-limitations.md=.
- *Exit*: both flag states produce correct, gate-passing binaries; the
  default is documented; the OFF-state's silent-wrap behaviour is
  written down next to the ON-state's overflow-error behaviour so a
  reader of =docs/runtime-limitations.md= is never left guessing which
  one shipped.

* §5 Verification design

** §5.1 Against-the-bug

The bug this doc exists to close is exactly the §1.2 probe. It becomes
the permanent regression case:

#+begin_src elisp
;; test/nelisp-fixnum-overflow-test.el (new)
(ert-deftest nelisp-native-add-overflow-signals ()
  (should-error (nelisp-eval '(+ most-positive-fixnum 1)) :type 'overflow-error))
(ert-deftest nelisp-native-mul-overflow-signals ()
  (should-error (nelisp-eval '(* 100000000000 100000000000)) :type 'overflow-error))
#+end_src

plus a =standalone-reader-*-smoke=-style Makefile target that runs the
*built binary* (not the host-Emacs ERT harness) against the same two
forms and asserts the process exits via a caught =overflow-error=
rather than printing a wrapped integer — this is the layer §1's
evidence says actually matters, so the gate has to exercise the built
=target/nelisp=, not just =nelisp-eval= under host Emacs.

** §5.2 Parity forms

Real Emacs never overflows a fixnum add/multiply (it promotes to a
bignum silently), so a literal value-for-value parity comparison
against stock Emacs would be *wrong* here — this is a deliberate,
documented divergence (§2), not a parity target. The parity form that
*does* apply is the boundary itself: =most-positive-fixnum=/
=most-negative-fixnum= must equal Emacs's own values exactly (already
verified, §1.2, and this doc changes nothing about that), and every
non-overflowing addition/multiplication within range must still match
Emacs bit-for-bit — the new checks must be provably no-ops on the
non-overflow path. A =nelisp-parity-probe= sweep over boundary-adjacent
values (=most-positive-fixnum - 2= through =+2=, and the same near
=most-negative-fixnum=) belongs in the P0/P1 exit criteria, checking
that only the exact boundary-crossing cases newly diverge (Emacs:
silent bignum promotion; NeLisp: loud signal) and nothing on either
side of it does.

* §6 Open questions

- *Cost, unmeasured*: §3.2 argues the x86_64 =jo= form is cheap in
  principle (a flag the hardware already computed, plus a
  branch-predicted-not-taken jump), but this doc does not carry a real
  measurement — P1's exit criterion requires one via
  =tools/ai/bench-compare.sh= (its slope/drift/identity guards, per
  =tools/ai/README.md=, are exactly what stops an arithmetic
  micro-benchmark here from repeating the "2.5x regression was
  background load" mistake that tool exists to prevent) before P3's
  feature-flag question can be answered either way.
- *Interaction with =nelisp_jit_add2=/=mul2= as leaves*: once
  =--emit-arith= (§1.4) is checked, does that also mean every call
  *through* =nelisp_jit_add2=/=mul2= (e.g. from
  =nl-jit-call-i64-i64= sites in =lisp/nelisp-stdlib.el= that use the
  =(nl-jit-call-i64-i64 "nelisp_jit_add2" 0 X)= idiom purely as a
  truncation/coercion trick, not as user-visible addition) becomes
  checked too, and is that ever semantically wrong for a call site that
  relies on the *wrap*, not the sum? =lisp/nelisp-stdlib.el:55-87= notes
  exactly this idiom ("All-int-trunc uses..."); an implementer must
  audit those call sites before flipping the default, since a coercion
  trick that *depends on* wraparound would break under the new checked
  semantics.
- *Bignum future*: this doc explicitly does not design bignum support
  (that is sibling doc 190's territory per this doc's mandate) — the
  question this doc leaves open for that doc is whether P3's
  documented-wrap OFF-state should be framed as permanent (a language
  decision) or as a placeholder pending bignum promotion (an
  implementation gap), since that framing changes what
  =docs/runtime-limitations.md= should say.
- *=/-= and other arithmetic subrs*: this doc scopes only =+=/=*=
  (matching the task's measured evidence and =expt='s existing
  precedent). =-= shares =wf_diff='s fold and the same emit-arith
  instruction family — P0/P1's implementer should decide in the same
  pass whether =-= gets the identical treatment (it almost certainly
  should, on consistency grounds) or is deliberately deferred; this doc
  takes no position and flags it rather than silently expanding scope.
