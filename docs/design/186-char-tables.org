* §0 TL;DR

The obvious framing of this doc — "char-tables are entirely absent, decide
between a real range-compressed structure and a hash-backed interim" — is
*wrong*, and re-verifying it against this branch's own build is what this
session spent most of its time on. A native =CharTable= type already
exists, tagged (=nelisp-sexp--tag-char-table= = 9,
=lisp/nelisp-sexp-layout.el:37,217=), fully wired through =aref=/=aset=
dispatch (=lisp/nelisp-jit-strategy.el:308-320,455-456,488-489,523=), GC
(=lisp/nelisp-cc-nlchartable-drop.el=, =-clone.el=), heap-image
serialization (=lisp/nelisp-heap-image.el:63,662=), and a dedicated
=nelisp-sys= DSL surface with its own ERT coverage
(=packages/nelisp-sys/test/nelisp-sys-backend-test.el:197-213=). Its
storage IS the "hash-backed interim" this doc was asked to weigh against a
real structure: =lisp/nelisp-cc-evalport-nonenv-char-table.el= implements
=nl_char_table_get_raw=/=nl_char_table_set_raw= as a growable, *linearly
scanned* =(key . val)= entry array with parent-chain fallback and a
default value — not Emacs's actual range-compressed ASCII+super-table+
sub-table structure. So the real vs. interim question was already decided,
by someone else, before this doc existed; the interim already ships.

What is missing is the *Elisp-visible* layer on top of that native type:
=make-char-table=, =char-table-p=, =char-table-parent=/=set-char-table-
parent=, =char-table-extra-slot=/=set-char-table-extra-slot=,
=char-table-range=/=set-char-table-range=, and every consumer built on
those — =standard-syntax-table=, =char-syntax=, =with-syntax-table=
(present only as a macro stub that discards its argument, =lisp/nelisp-
stdlib-eval-special.el:207=), =standard-case-table=/=current-case-table=.
None of these twelve names is =fboundp= on this branch's =target/nelisp=
(confirmed by direct probe, §1.1).

*Measured consumer priority (§1.4, contradicting the task background's
guess)*: =upcase=/=downcase= do NOT need char-tables — they already work,
correctly and Unicode-aware, via a hardcoded range predicate
(=nelisp--case-up-char=/=-down-char=, =scripts/nelisp-stdlib-prelude.el:
874-975=) with zero dependency on any case-table. The real, currently
broken consumer is the *regex engine's* =\sC= syntax-class escape
(=lisp/nelisp-stdlib-regexp.el:315-320=), which the file's own comment
admits is wrong in a stated direction ("every =\\sC= behaved as =\\s-=")
because syntax-class parsing has nowhere to look anything up. =\w=/=\b=
work today only because a hardcoded ASCII word-constituent predicate
happens to match Emacs's *default* standard syntax table for ASCII input
— it cannot be customized and is silently wrong for anything a real
syntax table would classify differently.

*Decided direction*: expose the existing native char-table as a thin
Elisp API (§3), accept the entry-array's O(n) lookup for now rather than
building real range compression (§3.3 bounds why), and let =\sC= (§3.4)
be the first real consumer — ahead of =syntax-table=/=case-table= objects,
which need buffer/point machinery this doc does not own (Doc 188).

** §1.2 The native representation that already exists

=nelisp-sexp--tag-char-table= (=lisp/nelisp-sexp-layout.el:37=, value 9)
is a first-class =Sexp= tag, on par with cons/string/vector. Storage
(=lisp/nelisp-cc-evalport-nonenv-char-table.el=, one =defconst= holding
six =defun= forms compiled into the =nonenv-char-table.o= unit):

#+begin_src elisp
(defun nl_char_table_get_raw (arg idx out)
  (let* ((tag (nelisp_ptr_read_u8 arg 0)))
    (if (= tag 9)
        (let* ((box (ptr-read-u64 (+ arg 8) 0)))
          (let* ((entries_ptr (ptr-read-u64 (+ box 64) 0))
                 (entries_len (ptr-read-u64 (+ box 80) 0)))
            (nl_ct_get_search box entries_ptr entries_len idx out 0)))
      1)))
#+end_src

=nl_ct_get_search= walks the entry array *linearly*, comparing each
=(key . val)= 40-byte entry's key against =idx=; on exhaustion it recurses
into the =parent= pointer (box offset 88) if set, else clones the
=default_val= (box offset 32) into =out=. =nl_ct_set_step=/=nl_ct_push_new=
append new entries, doubling capacity via =nl_ct_grow_entries= when full
— this is exactly the "hash/list-backed interim... exposing the API
surface without the real sparse-range internals" the task background
asked this doc to weigh as an option. It already exists; the design
question this doc actually faces is narrower: expose it, or replace it.

The box layout (=lisp/nelisp-cc-nlchartable-drop.el:14-31=, historically
attributed to a since-deleted =build-tool/src/eval/nlchartable.rs= — this
repo carries no Rust at all today, confirmed by =find . -name '*.rs'=
returning nothing; the layout survives only as this comment and the
elisp kernels that implement it) reserves, but nothing above this layer
exposes:

| field | offset | size | Elisp-visible today? |
|---|---|---|---|
| subtype | 0 | 32B (Sexp) | no (=char-table-subtype= absent) |
| default_val | 32 | 32B (Sexp) | only as aref fallback, no accessor |
| entries | 64/72/80 | 24B (Vec header: ptr/cap/len) | no direct accessor (internal only) |
| parent | 88 | 8B (Option<NlCharTableRef>) | no (=char-table-parent= absent) |
| extra | ~96 | 24B (Vec<Sexp>, reserved) | no (=char-table-extra-slot= absent) |

Dispatch already routes =aref=/=aset= on a char-table-tagged value through
this storage (=lisp/nelisp-jit-strategy.el:455-456,488-489,523=), and the
=nelisp-sys= compiler DSL has first-class =sys:char-table-get=/=sys:char-
table-set!= forms lowering to =nl_char_table_get_raw=/=set_raw=
(=packages/nelisp-sys/src/nelisp-sys-frontend.el:407-429=,
=-backend.el:160-168=), with dedicated ERT coverage of that lowering
(=packages/nelisp-sys/test/nelisp-sys-backend-test.el:197-213=). None of
this has an Elisp-level entry point that could ever reach it, because
nothing allocates a =CharTable= box from Elisp — there is no
=nl_char_table_new=/=char-table-new= anywhere in the tree (confirmed by
grep across =*.el=).

** §1.3 The one real call site is dead code

=make-char-table= has exactly one call in the whole repository:

(let ((table (make-char-table 'nelisp-b64--decode-table nil))
      (index 0))
  ...)

This package is not load-bearing for anything the standalone build
actually ships. The real =base64-decode-string=/=base64-encode-string=
used throughout the tree (=lisp/nelisp-artifact.el:347,352,1364,1366=,
=scripts/nelisp-standalone-build.el:15281,18447=) come from the prelude's
own implementation (=scripts/nelisp-stdlib-prelude.el:7574=), which does
not use a char-table at all — confirmed by probe:
=(fboundp 'base64-decode-string)= is =t= in a fresh binary with no
package required, and =packages/nelisp-base64= is not required by
=nelisp-artifact.el=, the prelude, or the standalone build script (only
false-positive substring matches on the generic phrase "base64-decode"
turned up in an initial grep; none was an actual =require=). If this
package is ever wired in, calling its decode path today hits a
void-function error at =make-char-table=, but nothing currently reaches
that path.

** §1.4 The real, currently broken consumer: regex =\sC=, not case ops

=upcase=/=downcase= (=scripts/nelisp-stdlib-prelude.el:911,950=, plus
=upcase-initials= at :929) implement Unicode case mapping via
=nelisp--case-up-char=/=-down-char=ta hardcoded ladder of range
comparisons (ASCII, Latin-1 supplement, and the Cyrillic-extended
=#x4D0-#x4FF= pair range at minimum — read in full at
=scripts/nelisp-stdlib-prelude.el:850-906=), including the one-to-many
=U+00DF -> "SS"= full-string-mapping special case Emacs itself
special-cases. None of this consults a case-table, a char-table, or
anything char-table-shaped: it is a closed-form function of the
character code. *Case operations do not need char-tables* — this
contradicts the task background's framing, and is the kind of
divergence a design doc re-verifying its own premises is supposed to
catch rather than propagate.

The regex engine, by contrast, is honest about being wrong today,
specifically because there is nowhere to look up a real syntax class:

#+begin_src elisp
;; lisp/nelisp-stdlib-regexp.el:296-320
(defun nlre--word-p (c)
  (or (and (>= c ?a) (<= c ?z)) (and (>= c ?A) (<= c ?Z))
      (and (>= c ?0) (<= c ?9))))
;; `\sC' matches a character whose SYNTAX CLASS is C.  The class character was
;; parsed and thrown away, so every \sC behaved as \s- (whitespace) and every
;; \SC as its negation: (string-match "\Sw" "a") answered 0 where Emacs
;; answers nil.  A class this does not model matches nothing, which is wrong
;; in a stated direction rather than in an arbitrary one.
#+end_src

=nlre--word-p= is a closed-form ASCII predicate that happens to agree with
Emacs's *default global* standard syntax table (where =_= is a symbol,
not word, constituent — the adjacent comment at :306-309 documents this
was gotten right on purpose, via a real regression:
=(string-match "\\bx" "_x")= previously answered nil where Emacs answers
1). It cannot be customized per major mode and has no path to
=modify-syntax-entry=. =\sC=/=\SC= have no implementation to fall back on
at all — every class is currently misread as whitespace/non-whitespace.
This is the first place a real syntax-table object would change an
observable, already-documented-as-wrong answer, and it needs no buffer,
no point, and no markers — only a syntax-table VALUE and a character, both
in scope for this doc.

** §1.5 =with-syntax-table= is a full stub

#+begin_src elisp
;; lisp/nelisp-stdlib-eval-special.el:207-209
(defmacro with-syntax-table (_table &rest body)
  "Stub: ignore TABLE, run BODY in current context."
  (cons 'progn body))
#+end_src

TABLE is discarded at macro-expansion time — this is a different failure
shape from the runtime-argument-ignored pattern
=tools/partial-accepted.txt= inventories (that file tracks =(defun f (...
_ignored-arg ...))=, not macros that drop a whole sub-form), so it does
not appear there; noted here so a future audit of that inventory does not
read its absence as "already reviewed."

* §2 Decided direction

*Expose the existing native char-table; do not build a second
representation.* The "real range-compressed structure vs. hash-backed
interim" choice the task background posed has a different answer than
either option once §1.2 is accounted for: the interim already exists,
already has GC/heap-image/JIT-dispatch integration, and replacing it with
a real Emacs-shaped range-compressed structure (fixed ASCII sub-table +
super-table + sparse sub-char-tables for the supplementary planes) is a
strictly bigger, riskier rewrite than this doc's measured consumer set
(§1.4: one regex escape class, currently ASCII-scoped) justifies.

| option | mechanism | verdict |
|---|---|---|
| Build Emacs's real range-compressed char-table structure from scratch | fixed top-level table + depth-1/2/3 sub-tables per Emacs's actual C layout | *rejected for this doc* — no measured consumer needs Unicode-scale range assignment yet; §3.3 bounds why the existing linear entry array is adequate for the actual near-term consumer (a syntax table over ASCII + Latin-1, on the order of 200-400 entries) |
| Build a NEW hash-table-backed char-table type, ignoring the existing native one | =make-hash-table= plus an Elisp-level API shim | *rejected* — throws away working GC/heap-image/JIT-dispatch integration (§1.2) to duplicate exactly what already exists, for no benefit |
| Expose the existing native =CharTable= tag via a thin Elisp constructor/predicate/accessor layer, accept O(n) lookup for now | =make-char-table=/=char-table-p=/=char-table-parent=/=char-table-extra-slot=/=char-table-range=/=set-char-table-range=, all thin wrappers over =nl_char_table_get_raw=/=set_raw= plus new allocation and parent/extra-slot accessors | *accepted* — §3 |

* §3 Design

** §3.1 Allocation: =nl_char_table_new= (the one missing native primitive)

Every accessor in §1.2 exists except a constructor. A new =nelisp-sys=
kernel, sibling to =nelisp-cc-evalport-nonenv-char-table.el=, allocates a
128-byte =NlCharTable= box (=alloc-bytes 128 8=, matching the layout in
§1.2's table: 32B subtype + 32B default_val + 24B empty entries Vec header
(ptr=0,cap=0,len=0) + 8B parent (0 = none) + 24B empty extra Vec header +
8B refcount=1), writes tag 9 into an output Sexp slot pointing at it, and
returns. This is new code, not exposure of something that silently
already works — flagged so the phased plan (§4 P0) does not undercount
it.

** §3.2 Elisp API surface

#+begin_src elisp
(make-char-table SUBTYPE &optional INIT)   ; alloc + set default_val = INIT
(char-table-p OBJECT)                       ; sexp-tag == 9
(char-table-subtype CHAR-TABLE)             ; read box+0
(char-table-parent CHAR-TABLE)              ; read box+88, nil if 0
(set-char-table-parent CHAR-TABLE PARENT)   ; write box+88
(char-table-extra-slot CHAR-TABLE N)        ; index into the reserved
(set-char-table-extra-slot CHAR-TABLE N V)  ;   `extra' Vec (§3.3 on growth)
(aref CHAR-TABLE CHAR)                      ; ALREADY WORKS (§1.2)
(aset CHAR-TABLE CHAR VALUE)                ; ALREADY WORKS (§1.2)
#+end_src

=aref=/=aset= need no new dispatch — =nelisp-jit-strategy.el:455-456,488-
489= already routes tag-9 values through =nl_char_table_get_raw=/
=set_raw=. Only allocation (§3.1) and the four pure accessor/mutator pairs
above are new.

** §3.3 =char-table-range=/=set-char-table-range= — scoped, not general

Emacs's real =set-char-table-range= accepts a single char, a =(FROM . TO)=
cons, =nil= (the default slot), or =t= (every char). Against §1.2's
linearly-scanned entry array, a naive =(set-char-table-range table
'(0 . 4194303) val)= would push 4.2M entries and make every subsequent
=aref= an O(n) scan of them — a real scaling trap, not a hypothetical
one, since nothing currently guards against it.

*Scope for this doc*: support the single-char and =(FROM . TO)= forms by
expanding the range into individual =nl_char_table_set_raw= calls (no
new native primitive), but ONLY up to a compile-time-checked entry-count
ceiling (proposed: 4096, comfortably above a full ASCII+Latin-1+Latin
Extended-A syntax table, which is the only near-term consumer, §1.4).
Above the ceiling, signal a distinct, loud error
(=char-table-range-too-large=, not a silent truncation or a silent slow
path) rather than accepting an assignment that would degrade every future
=aref= on that table. =t= (every character) is explicitly OUT of scope —
it has no honest small-N encoding on top of the entry array — and
signals the same way. Real range compression (a default-value-per-block
scheme, short of Emacs's full sub-char-table structure) is filed as
§7.2, not designed here, because no consumer measured in this doc needs
it yet.

** §3.4 First real consumer: regex =\sC=/=\SC=

Once §3.1-§3.2 land, =lisp/nelisp-stdlib-regexp.el='s =\sC= handling
(§1.4) gains a real implementation: a module-level =nlre--syntax-table=
char-table (populated at load time with Emacs's standard-syntax-table
defaults for ASCII — word/symbol/whitespace/punctuation classes, the
same four classes =nlre--word-p=/=-symbol-p=/=-space-p= already encode by
hand) replaces the "parsed and thrown away" class byte with a real
=(aref nlre--syntax-table c)= lookup. This is the FIRST place this doc's
new API is load-bearing for something other than its own tests, and is
scoped narrowly: no per-buffer/per-mode syntax table yet (that needs
=current-buffer=, Doc 188's territory), just a single global default
table replacing four hand-written predicates with one data-driven one —
a refactor that is also a strict correctness improvement (=\sC=/=\SC= for
classes beyond whitespace start working; §1.4's documented divergence
closes).

** §3.5 =standard-syntax-table=/=with-syntax-table=/case-table objects — named, not built here

=standard-syntax-table=, =syntax-table=, =char-syntax=, =current-case-
table=, real per-buffer =with-syntax-table= dynamic scoping, and
=forward-word=/=skip-syntax-forward= all need a *current buffer* to bind
against — building them here would either invent a buffer-shaped global
this doc does not own, or duplicate work Doc 188 (buffer unification) is
already scoped to do. This doc's contribution to that later work is
narrow and concrete: the char-table type they will all be backed by
already exists and is now Elisp-constructible (§3.1-§3.2), and §3.4
already gives the regex layer a working default table to hand off from
when Doc 188 wires up per-buffer syntax tables. =with-syntax-table='s stub
(§1.5) stays a stub until Doc 188 has a buffer to bind it against —
fixing the macro to dynamically rebind a *global* placeholder variable
instead of a real buffer-local one would be worse than the current honest
no-op, since it would silently claim per-buffer scoping that does not
exist.

* §4 Phased plan with costs

Effort estimates are engineer-days for an implementer following this doc,
on the pattern of Doc 164 §6.

** P0 — =nl_char_table_new= + =make-char-table=/=char-table-p=  (1 d)
- New allocation kernel (§3.1), wired through =compile-elisp-objects.el=
  the same way =nlchartable-clone.o=/=-drop.o= already are
  (=scripts/nelisp-standalone-build.el:12838= is the existing sibling
  entry to extend).
- =char-table-p= as a tag-9 check (mirrors any existing =*-p= predicate
  over a Sexp tag, e.g. =bufferp=/=processp='s shape — same one-line
  pattern, no new mechanism).
- *Exit*: =(char-table-p (make-char-table 'test nil))= is =t= on
  =target/nelisp=; =(aref (make-char-table 'test 'DEFAULT) ?a)= returns
  =DEFAULT= (proves the constructor's default_val write and the already-
  working =aref= fallback path compose correctly).

** P1 — parent/extra-slot/subtype accessors  (0.5–1 d)
- The four read/write pairs in §3.2's second half.
- *Exit*: =(set-char-table-parent child parent)= followed by =(aref child
  CHAR-NOT-IN-CHILD)= returns the value =aref='d from =parent= directly
  (proves the fallback chain §1.2 already implements natively is now
  reachable end-to-end from Elisp).

** P2 — =char-table-range=/=set-char-table-range=, ceiling-guarded  (1–1.5 d)
- The expand-to-individual-=aset= implementation plus the
  =char-table-range-too-large= ceiling (§3.3).
- *Exit*: =(set-char-table-range table '(?a . ?z) 'lower)= populates 26
  entries correctly; a range exceeding the ceiling signals the new error
  symbol rather than silently truncating or silently accepting.

** P3 — regex =\sC=/=\SC= real implementation  (1–2 d)
- The =nlre--syntax-table= default table (§3.4) and the class-lookup
  rewrite in =lisp/nelisp-stdlib-regexp.el=.
- *Exit*: =(string-match "\\sw" "a")= and =(string-match "\\s_" "_")= both
  match (currently both misclassify per §1.4); =(string-match "\\Sw" "a")=
  is =nil= (currently a false match) — all three added to the
  =emacs-parity= cases file (§6.2) so the fix is pinned against a real
  Emacs comparison, not only an internal assertion.

** P4 — dead-code correction: =packages/nelisp-base64=  (0.25 d, optional)
- Now that =make-char-table= exists, =nelisp-base64--ensure-decode-table=
  (§1.3) stops being a latent void-function trap if the package is ever
  wired in. No behavior change to anything currently shipped (§1.3
  confirmed it is unreached); this phase is bookkeeping, not a fix to a
  live bug, and can be dropped from a minimal cut without affecting P0-P3.

* §5 Cost

Every new code path in §3 is either (a) allocation, called once per
char-table construction, not per-character — no hot-path concern, or (b)
already-existing =aref=/=aset= dispatch (§1.2), completely unchanged by
this doc. The one place this doc's cost claim needs to be more than
assertion is §3.4's regex integration, since =\w=/=\b= sit in the regex
engine's per-character match loop: replacing four inlined range
comparisons (=nlre--word-p= etc., each 1-3 integer compares) with one
=(aref nlre--syntax-table c)= trades a few inlined branches for a
function call plus a linear scan capped at the table's real entry count
(low hundreds, §3.3). This is the kind of claim =AI.md= rule 3 requires
measuring rather than asserting: P3's exit criterion should include a
=bench-compare.sh= two-arm run (pattern per Doc 187 §4/§5, which faces the
identical "bound a per-character hot-path cost honestly" problem) of a
representative =\w=-heavy regex before/after, reported as a guarded ratio
rather than assumed negligible.

* §7 Open questions

** §7.1 Where exactly does allocation belong

§3.1's =nl_char_table_new= needs a home in the =nelisp-sys= DSL frontend/
backend (=packages/nelisp-sys/src/nelisp-sys-frontend.el=/=-backend.el=,
which already has =sys:char-table-get=/=sys:char-table-set!= but no
=sys:char-table-new=) or can be written directly as a =lisp/nelisp-cc-*=
kernel the way =nl_char_table_get_raw= already is, bypassing the DSL.
This doc does not resolve which — the DSL path gets ERT coverage "for
free" via the pattern at =nelisp-sys-backend-test.el:197-213=, the direct
kernel path is less code. Left to the implementer, flagged so it is a
choice rather than an accident.

** §7.2 Real range compression, deferred

§3.3's entry-count ceiling is a guard against a real problem, not a
solution to it. If a future consumer needs (for example) a
supplementary-plane-aware case-table or a large custom syntax table, the
linear entry array stops being adequate well before Unicode's full range.
A depth-limited block/default scheme (not Emacs's full multi-level
sub-char-table structure, which this doc has no measured consumer to
justify) is the likely next step; not designed here because §1.4 found
no consumer that needs it yet.

** §7.3 Interaction with Doc 188

§3.5 deliberately stops short of =standard-syntax-table=/per-buffer
=with-syntax-table=/=forward-word=. Doc 188 (buffer unification, a
sibling doc in this same batch) should confirm it is willing to own that
handoff — this doc's author has not read Doc 188 and cites it only as a
forward reference, per the convention Doc 187 §7.4 sets.

** §7.4 Whether =\s-=-class default coverage is complete enough for P3

§3.4 sketches four syntax classes (word/symbol/whitespace/punctuation)
because those are what =nlre--word-p=/=-symbol-p=/=-space-p= already
distinguish. Emacs's standard syntax table has more classes
(open/close-parenthesis, string-quote, escape, comment-start/end, ...).
Whether P3 needs the fuller set to be a real correctness win, or whether
the four-class subset is sufficient for every =\sC= form actually reached
by anything in this tree's test corpus, is not measured in this session
and should be checked before P3 is scoped as "done."
